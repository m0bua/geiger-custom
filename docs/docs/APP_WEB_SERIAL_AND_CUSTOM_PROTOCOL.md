# Geiger‑2: стоковий додаток, Web Serial, RTS/DTR та протокол кастому

Дата: 2026-10-21. Пристрій: Mira Safety Geiger‑2 / HiStand, STM32L051C8T6.

## Актуальність статусу

Цей звіт зберігає аналіз стокового застосунку та хронологію протокольних і
фізичних тестів 2026-10-21/22. Станом на 2026-10-23 у репозиторії вже є
працюючий браузерний клієнт; його поточні вкладки й інструкція запуску описані
в [`app/README.md`](../../app/README.md). У вкладці Firmware є секція Reboot:
Firmware повторює документований етап запуску прикладної прошивки; Bootloader
перевіряє ROM ACK у 115200 8E1 після послідовності RTS/DTR high/high → low/high.
Це експериментальний Web Serial шлях,
бо фізична відповідність логічних рівнів не встановлена; запис прошивки не виконується.
Користувач попередньо підтвердив, що цикл Firmware ↔ Bootloader виглядає робочим;
повторні цикли ще потрібні.
Твердження нижче про непідтверджене
підключення стосуються часу виконання тих тестів і не є описом актуальної
готовності застосунку. Прошивання HEX/BIN і дампи FLASH/EEPROM/SPI вже
реалізовані у вкладці Firmware; синхронізація часу через клієнт ще не реалізована.

## 1. Висновки

**Аналог додатка можна зробити як браузерний HTML/CSS/JavaScript без Electron, Node.js, native modules та STM32_Programmer_CLI.** Телеметрія, статистика, налаштування кастому, імпорт/експорт і навіть окремий STM32 UART bootloader-клієнт технічно реалізуються в JS.

Однак **«додаток працює без бінарників» і «підключення гарантовано не спричинить жодного reset» — різні вимоги**. Web Serial керує RTS/DTR лише після відкриття COM-порту. API не гарантує відсутність коротких небажаних переходів при open/close. Якщо міст через ці лінії апаратно керує NRST/BOOT0, зміна протоколу статистики або кастомна прошивка не завадять фізичному reset.

Практичний вибір:

- для початкового кастому — Web Serial, один постійно відкритий порт, фіксовані 115200 8N1, hardware flow control вимкнений;
- протокол — бінарні кадри COBS + CRC‑16, номер запиту, тип операції й довжина;
- налаштування — типізовані поля з версією/ревізією та окремим commit;
- статистика — читання блоками зі знімка, підтримка resume та виявлення перезаписаного кільця;
- прошивання — окремий сервісний режим; жодних автоматичних reset через звичайний timeout телеметрії;
- вимога абсолютної відсутності reset потребує перевірки апаратного reset/boot тракту. За нинішніх даних універсальної програмної гарантії немає.

Файли додатка вже були надані: **повторно надсилати їх зараз не потрібно**.

## 3. Як MilerdPort спілкується з HiStand

### Виявлення і native-залежності

`Port.ts` розпізнає HiStand переважно за manufacturer `Silicon Labs`. Це ознака сімейства USB–UART мосту, не підтвердження точного номера CP210x. Перевірка списку портів відбувається приблизно раз на секунду.

Додаток — Electron із React. `window.require('serialport')` використовує native bindings; updater окремо запускає STM32_Programmer_CLI. Обидві ці залежності можна прибрати в новому браузерному клієнті.

У Web Serial сайт бачить дозволені користувачем порти й USB VID/PID, а не довільно сканує всі COM-порти як native-застосунок. Один раз потрібний вибір пристрою користувачем; далі можна працювати з уже дозволеним портом.

### Розбіжність parity — підтверджена

| Джерело / режим | Налаштування |
|---|---|
| MilerdPort `getSerialPort()` для HiStand | 115200, 8 data bits, **even**, 1 stop bit |
| Наданий HEX, робоча прошивка | 115200, 8 data bits, **no parity**, 1 stop bit |
| STM32 ROM UART bootloader, окремий сервісний режим | 8E1 за AN3155 для цього сімейства |

За `0x08002CCC` HEX записує WordLength=0, StopBits=0, Parity=0, Mode=0x0C. Оригінальний HAL формує USART1 CR1=0x0000000D після enable; CR2=0, CR3=0. PCE та M0/M1 не встановлені. При штатному PCLK2=32 МГц BRR=0x116.

Тобто попереднє твердження «HiStand завжди 8E1» описувало **налаштування додатка**, але не відповідало конфігурації саме цього HEX. Несумісність parity здатна створювати framing/parity errors і пошкоджені відповіді; її реальний прояв залежить від приймача/драйвера. Не пояснювати всі проблеми зв’язку лише RTS/DTR.

Для нового кастому обрати формат явно. Рекомендую 8N1 у робочому режимі; ROM bootloader лишити окремим 8E1 режимом. Якщо буде потрібно відновлення з ROM в межах одного open, можна обрати для кастому 8E1, але це окремий компроміс і не усуває апаратних reset.

### Команди робочої прошивки

Команди — **рівно 4 ASCII-байти без CR/LF і без NUL**. RX completion повторно викликає `HAL_UART_Receive_IT(handle, 0x20000104, 4)`; parser головного циклу перевіряє ці 4 байти. Зайвий `\n` зрушує межі наступних команд.

| Команда | Що повертає / робить HEX | Примітки клієнту |
|---|---|---|
| `fwid` | 6 байтів `4.1.17` | Не чекати newline |
| `dvid` | Фрагменти hex-рядка з UID STM32, сумарно 27 переданих байтів | Fixed-length передача після `%x`, можливі NUL/залишкові байти при короткому результаті форматування |
| `dose` | **CPM**, `%04d`, передає рівно 4 байти | Назва не означає накопичену дозу або µSv/h |
| `batt` | Заряд `%03d`, 3 байти | Наприклад `055`; від 1670 raw обмежує на 100 |
| `slrb` | Сонячний raw/31, 3 байти | Команда є в HEX; основний опитувальний цикл додатка її не використовує |
| `date` | `HH:MM`, потім `DD/MM/YY`, разом 13 байтів | Між двома частинами немає переданого роздільника |
| `stat` | Секції `acc:`, `max:`, `lim:` | По 32 значення; формат нижче |
| `tset` + наступні 4 байти `HHMM` | Встановлює час | Приклад: `tset`, пауза, `1234` |
| `dset` + наступні 4 байти `DDMM` | Встановлює день/місяць | Не MMDD |
| `yset` + наступні 4 байти `YYYY` | Використовує останні дві цифри року | Наприклад `2026` → 26 |

Непідтримані команди не мають загальної структурованої error-відповіді. Формального request ID, CRC та єдиного response envelope немає. Після команд встановлення часу окремого ACK у досліджуваній гілці не видно.

Перевірені приклади фактичної передачі з оригінального коду:

```text
fwid -> 34 2E 31 2E 31 37       "4.1.17"
dose при CPM=23 -> 30 30 32 33  "0023"
batt при raw=1500 -> 30 35 35  "055"
dose при CPM=12345 -> "1234"   // обрізання через TX length=4
```

За `dose` немає числа з плаваючою комою: `0x0800431E` бере uint16 CPM із `0x20000196`. У UI MilerdPort сам множить поточне значення на 0.0066 для µSv/h або 0.66 для µR/h. Це відрізняється від відновленого точного stock коефіцієнта 0.00666. Для нового додатка використовувати коефіцієнт приладу, не дублювати різні константи у firmware та UI.

### Важливий побічний ефект синхронізації часу

Після **кожної** гілки `dset`/`tset`/`yset` код проходить через `0x08003EE8–0x08003FC4` і очищає лічильник дози, накопичену double-дозу, історичні RAM-масиви та секундне кільце. Це перевірено виконанням усіх трьох гілок із ненульовими тестовими даними.

Тому синхронізація часу стоковим застосунком може обнулити вимірювальну сесію/історію. У кастомі час має встановлюватися окремим anchor без очищення логу. Видалення статистики — окрема явна команда.

### Статистика `stat`

HEX передає:

```text
acc: + 32 * (10 десяткових цифр + ',')
CR LF
max: + 32 * (5 десяткових цифр + ',')
lim: + 32 * (2 десяткові цифри + ',')
```

Для значень у межах ширини формату — 654 передані байти. `acc` — накопичені CNT за RAM-слотами днів, `max` — максимум CPM, `lim` — рівень індикатора дози. Це не MIN/MAX/AVG усіх наших майбутніх агрегатів і не лог кожного спрацювання.

MilerdPort збирає текст, ділить за `acc:|max:|lim:`, потім за комами й сам призначає дати назад від поточного дня ПК. У відповіді немає timestamp кожного слота. Невідомий час/паузи/перезапуск приладу так не відновлюються.

Завершальна кома залишає порожній елемент; `.map(Number)` перетворює його на 0, якщо його не прибрати. Новий parser має перевіряти рівно 32 значення кожної секції, NUL, часткові відповіді й коректність дат.

### Реальна послідовність додатка

Початкове опитування: open → 2 с → `fwid` → 1 с → `dvid` → 1 с → `batt` → 1 с → `date` → 1 с → close. Потім окремий open для `stat` із фіксованими очікуваннями, close, ще один open для телеметрії.

Телеметрія: `dose`, `batt`, `date`, приблизно по секунді очікування після кожної команди; додаткова пауза можлива при оновленні дати. Містить лише 40 локальних точок поточного показника; нова точка додається при зміні значення. Це не гарантований рівномірний часовий ряд.

У кількох шляхах код вважає один callback `data` однією відповіддю. Реальний serial stream може розрізати відповідь або об’єднати кілька фрагментів. Надійний JS-клієнт має накопичувати байти й розбирати їх за протоколом; для стоку — по одній команді з очікуваною довжиною/структурою, без pipeline.

Повторні open/close та автоматичний reset при помилці `parseInt(batt)` у цьому додатку — невдала основа для нашого випадку з керувальними лініями.

## 4. RTS/DTR: що справді робить додаток

### Звичайна робота

Після кожного `open` `getSerialPort()` викликає:

```js
port.set({ rts: false, dtr: false });
```

Це робиться **після відкриття**, а не атомарно з ним. Окрема функція reset відкриває порт, виставляє true/true, чекає 1 с і закриває його.

### Оновлення прошивки — знайдено повну послідовність

`pages/Devices/HiStand/DevicePage.tsx` запускає зовнішній CLI з такими буквальними аргументами:

| Етап | RTS у CLI | DTR у CLI | Додаткова дія |
|---|---|---|---|
| Вхід/перезапуск для оновлення | `high` | `high` | `-c port=... br=115200 p=even` |
| Запис | `low` | `high` | `-w <firmware.hex>` |
| Запуск програми | `high` | `low` | Окремий запуск CLI |

Це узгоджується з користувацьким спостереженням high/high → bootloader, high/low → прошивка. Для входу й роботи потрібна **послідовність станів**, а не одна постійна комбінація. При зміні рівня може відбуватися release reset або вибір BOOT0.

Назви `high/low` у STM32 CLI, булеві rts/dtr у native SerialPort, булеві Web Serial та фізичні вольти на виходах мосту не слід ототожнювати без перевірки. Лінії можуть бути active-low, а плата — містити інверсію/транзистори.

Прошивка STM32 налаштовує USART1 TX/RX PA9/PA10 AF4 без hardware flow control. Досліджуваний parser не читає RTS/DTR як звичайні команди. Точне підключення USB-мосту до NRST/BOOT0 HEX не встановлює; апаратний характер reset тут є висновком із поведінки та updater-послідовності.

## 5. Що Web Serial дозволяє і чого не гарантує

Станом на досліджений стандарт від 2026-10-19:

- `setSignals()` має `dataTerminalReady`, `requestToSend`, `break`.
- Виклик до завершення `open()` відхиляється як InvalidStateError.
- `SerialOptions` у `open()` містить baudRate/dataBits/stopBits/parity/bufferSize/flowControl, **не містить початкових DTR/RTS**.
- Зміна обох ліній одним `setSignals` не є гарантовано атомарною; стандарт описує застосування DTR, потім RTS.
- `getSignals()` повертає CTS/DSR/DCD/RI, але **не зчитує назад DTR/RTS**.
- `flowControl: 'none'` вимикає hardware handshake, але не гарантує відсутності переходів DTR/RTS при open/close.
- Стандартний `reconfigure()` для baud/parity без close/open відсутній у дослідженому IDL.

Отже, твердження «браузер узагалі не вміє RTS/DTR» неправильне. Правильне обмеження: **браузер не дає гарантовано задати безпечні стани до відкриття й усунути всі переходи ОС/драйвера**.

Приклад відкриття для кастому з 8N1:

```js
const port = await navigator.serial.requestPort();
await port.open({
  baudRate: 115200,
  dataBits: 8,
  parity: 'none',
  stopBits: 1,
  flowControl: 'none',
  bufferSize: 8192,
});

// Не задавати RTS/DTR навмання: браузерні setSignals-послідовності
// на тестованому приладі заводили MCU в bootloader.

// Далі один reader, один серіалізований writer, порт не закривати між запитами.
```

Цей приклад не обіцяє «нуль reset» при самому open. Не додавати окремий reset після кожної помилки зв’язку. Зміна вкладки UI також не має закривати порт.

Прямий браузерний доступ залежить від підтримки Web Serial; для першої версії орієнтир — настільний Chrome/Edge з перевіркою `'serial' in navigator`, secure context HTTPS/localhost і явним вибором порту. Драйвер USB–UART ОС все одно потрібний. «Без бінарників» тут означає без нашого native helper/CLI, а не без браузера/системного драйвера.

## 6. Як обходити проблему reset

| Варіант | Що реально дає | Обмеження |
|---|---|---|
| Web Serial із контрольованим reconnect | Найуніверсальніший браузерний доступ; можна прийняти можливий reboot/reconnect | Безпечна послідовність RTS/DTR поки не знайдена; тестовані варіанти зупиняли пристрій або заводили в bootloader |
| OS-specific native helper/transport | Дає змогу керувати початковою конфігурацією порту до/під час open; один профіль Windows на COM3 відкрився/закрився без reboot | Поки підтверджений лише один Windows-тест; потрібні окремі реалізації/перевірки для ОС і драйверів |
| Контрольована процедура запуску прошивки після небажаного bootloader | Відновлює зв’язок без native CLI, коли відома послідовність | Reset уже відбувся; можлива втрата останнього RAM-буфера |
| Налаштування USB-мосту/його драйвера | Іноді змінює початкові стани/поведінку | Потрібно встановити точну модель мосту й документовані можливості; не припускати універсальність |
| Апаратно відокремити automatic reset/boot від RTS/DTR або дозволяти його тільки сервісним перемикачем | Усунення фізичної причини reset при відкритті | Потребує роботи з платою й окремого способу сервісного входу |
| WebUSB прямо до мосту | Потенційно дає доступ до його vendor control transfers у JS | Залежить від chip/OS/USB driver; на Windows може вимагати інший binding. Не універсальна заміна Web Serial |
| Інший UART протокол: JSON/COBS/Modbus | Змінює передавання даних | **Не впливає на фізичні NRST/BOOT0** |

**Поточне рішення відкладене:** спершу продовжити функціонал і протокол. Пізніше порівняти дві опційні стратегії: Web Serial з прийнятним reboot/reconnect та OS-specific native transport для тих платформ, де потрібне відкриття без reboot. Тест native-профілю — лише доказ здійсненності для конкретного Windows/COM3, а не гарантія для всіх адаптерів чи ОС. Кастом не може виконувати код, поки NRST утримується активним, або якщо MCU завантажив ROM замість нього.

Не змінювати навмання option bytes або постійну конфігурацію USB-мосту заради цього обходу. Поки не відомі точна схема й поточні значення, це не обґрунтований програмний крок.

### Фізичні перевірки 2026-10-22

На ПК встановлений офіційний MilerdPort **1.7.0**: `serialport 12.0.0`, native binding `@serialport/bindings-cpp 12.0.1`. HiStand налаштовує 115200 8E1. У Windows binding застосовує DCB під час native open; його профіль не еквівалентний браузерному `open()` з наступним `setSignals()`.

- PowerShell native probe на COM3 застосував 115200 8E1, DTR enabled / RTS disabled у DCB, далі очистив RTS і потім DTR. Користувач підтвердив: відкриття й закриття порту пройшли без reboot. Скрипт: `tools/geiger2_native_open_probe.ps1`.
- Web Serial без `setSignals()` залишав прилад неактивним протягом відкритої сесії; після timeout-помилки й закриття порту прилад запустився. Це узгоджується з проблемою стану ліній при open/close, але не встановлює, яка саме фізична лінія/подія це спричиняє.
- Web Serial із пост-open зміною RTS/DTR у перевірених варіантах приводив до bootloader. Не вважати логічний стан `false,false` безпечною універсальною послідовністю.
- Окремий `System.IO.Ports.SerialPort` probe та STM32 CLI тест також приводили до небажаної поведінки; це не тотожне native-профілю офіційного застосунку й не спростовує успішний native Win32 probe.

Точне електричне відображення RTS/DTR на NRST/BOOT0, інверсії та перехідні процеси не вимірювались. Тому «лінії керування ймовірно впливають на reset/boot» — робоча гіпотеза, не доведена схема. Подальше дослідження підключення відкладене; не повторювати перебір RTS/DTR без окремо контрольованого плану.

### Журнал невдалих спроб підключення та входу в bootloader

Нижче зібрані практичні спостереження з цієї плати. Це не повна матриця станів RTS/DTR: не для кожної спроби збережено точні лінійні рівні, ОС/браузер чи момент переходу. Не трактувати кореляцію як доведене електричне керування NRST або BOOT0.

| Спроба | Спостереження | Висновок / обмеження |
|---|---|---|
| Web Serial: вибір порту й підтвердження підключення | Прилад перезапускався одразу після підтвердження; після цього інтерфейс іноді підключався, іноді від'єднувався і швидко підключався знову | Звичайний open браузерного порту вже може супроводжуватися reset/reconnect; прикладний протокол ще не почав передавати дані |
| Web Serial з різними перевіреними комбінаціями сигналів, зокрема експериментальною опцією | Частина варіантів заводила прилад у ROM bootloader; з експериментальною опцією прилад виглядав вимкненим і запускався після відпускання порту. В іншому тесті лишався вимкненим до повідомлення «Прилад не відповів…»/закриття порту, після чого запускався | Не знайдено безпечної універсальної post-open комбінації. Закриття/відпускання порту пов'язане з поверненням живого запуску, але точний механізм невідомий |
| STM32CubeProgrammer CLI, `stm -c port=COM3 br=115200 dtr=low rts=low` | Порт відкрився, пристрій ідентифіковано як STM32L05x/L06x/L010, Chip ID `0x417`, 64 KiB. Попри явно вказані low/low, прилад перезапустився; користувач спостерігав перехід у bootloader | Одна CLI-конфігурація low/low не запобігла reset/bootloader. Вивід підтверджує відповідь ROM-інтерфейсу під час цієї спроби, але не стан ліній на ніжках MCU |
| Початковий `geiger2_serial_probe.ps1` | Скрипт не отримав валідної відповіді протоколу за 5 секунд і вивів попередження, що пристрій міг перейти в ROM bootloader або профіль порту неправильний; користувач підтвердив, що опинився в bootloader | Timeout/відсутність відповіді не відрізняє bootloader від завислого, вимкненого чи неправильно налаштованого порту. Не надсилати bootloader sync автоматично за одним timeout |
| `geiger2_native_open_probe.ps1`, перша спроба | Не запустився через типізацію `desiredAccess` у PowerShell (`-1073741824` не конвертувався в `UInt32`) | Помилка була локальною в тестовому скрипті, не результатом взаємодії з пристроєм; аргумент виправили на беззнакове представлення |
| Той самий native Win32 probe після виправлення | Відкрив COM3 профілем 115200 8E1, DTR asserted у DCB / RTS deasserted, потім очистив RTS і DTR у порядку офіційного binding; жодних UART-байтів чи reset/bootloader-команд не надсилав. Під час спостереження прилад спочатку вимкнувся, а запустився тільки після timeout-повідомлення APP та закриття порту; користувач повідомив, що закриття порту передувало power-off/поверненню | Результат не є «підключенням без впливу»: open/close без UART-команд усе одно змінював стан приладу. Неоднозначно, чи це reset, power-off/hold, чи інший стан; сам probe не підтвердив обмін. Скрипт: `tools/geiger2_native_open_probe.ps1` |

Підсумок: успішний виклик native `CreateFile` або відсутність UART-передачі **не гарантує** безпечного стану приладу. З іншого боку, одиничний native probe раніше був описаний як open/close без reboot; пізніше спостереження уточнило, що прилад усе ж вимикався під час сесії та відновлювався біля її завершення. Для handoff пріоритет має це уточнене спостереження. Жодна спроба поки не підтвердила стабільний протокольний обмін із пристроєм без reboot/bootloader-переходу.

Перед реалізацією firmware update у APP необхідно відокремити звичайне підключення від явно запущеного сервісного оновлення. Не робити автоматичного входу в bootloader при connect, не слати `0x7F` за звичайним timeout і не вважати розрив/повторне підключення доказом успіху. Спочатку потрібен відтворюваний, контрольований спосіб повернути MCU до кастомної прошивки після невдалого входу в ROM та перевірка збереження/втрати RAM-даних при таких переходах.

Що лишається: встановити електричну відповідність RTS/DTR, порівняти профілі на інших ОС/адаптерах і підтвердити стабільний HELLO/GET_STATUS після відкриття порту. Read-only діагностика `boot_session`, `reset_cause`, `uptime` та UART error counters буде корисною, коли повернемось до цього функціоналу.

## 7. Чи потрібен CLI для прошивання

MilerdPort використовує CLI як готовий інструмент, але STM32 ROM говорить документованим байтовим протоколом AN3155. JS може відправляти sync `0x7F`, читати ACK `0x79`, запитувати supported commands/ID, виконувати дозволені read/write/erase та запуск програми. Обов’язково врахувати конкретну ROM-версію, карту Flash й AN2606 для MCU.

HEX — текстовий формат даних. Його parser, checksum, адресні діапазони та формування блоків можна написати в чистому JS. Прошивка як HEX/BIN лишиться необхідним вхідним файлом; зовнішня виконувана програма для передачі цих байтів не є технічно обов’язковою.

Водночас потрібні окремі перевірки ACK, timeout, read-back, діапазонів і відновлення. Аплет ROM не зобов’язаний читати нашу зовнішню SPI Flash: її обслуговуватиме кастом або спеціальна сервісна прошивка з власними командами.

Сервісний bootloader-клієнт тримати окремим від основного протоколу вимірювань. Не слати `0x7F` або reset-імпульси автоматично після одного пропущеного HELLO. Timeout не є доказом, що пристрій уже в ROM. Якщо потрібне автоматичне відновлення, явно визначити його умови й вплив на дані.

Зміна runtime 8N1 ↔ ROM 8E1 у браузері наразі вимагає close/open і знову зачіпає питання RTS/DTR. При режимі ROM відпустити апаратний reset перед спробами UART-команд; при утриманому NRST жоден протокол не допоможе.

## 8. Рекомендований протокол кастому v1

Це проєктна пропозиція, не опис уже наявної реалізації.

### Чому бінарний UART

Наявна фізична лінія — USB–UART → USART1. Формат байтів можна змінити кастомом без заміни цього тракту. Wi‑Fi/BLE потребують відповідного обладнання; STM32L051C8 не перетворюється на нативний USB CDC пристрій просто від зміни протоколу.

JSON по рядках був би простим для відлагодження, але для великих логів створює зайвий обсяг і parser на MCU. Рекомендую один невеликий бінарний протокол для всіх операцій. JSON залишити для export/import у браузері, CSV — для таблиць.

Не прив’язувати serial кадри до секторів або фізичного layout SPI. Прошивка має віддавати логічні records/блоки з явною версією формату; внутрішній storage layout тоді можна змінювати.

### Формат кадру

```text
wire = COBS(raw) + 00

raw = version:u8 | kind:u8 | request_id:u16 | opcode:u16 | length:u16
      | payload[length] | crc16:u16
```

Усі багатобайтові числа — little-endian. CRC рахується по header+payload, перед COBS. Для v1:

```text
version = 1
kind = 1 request / 2 response / 3 event
max payload = 512 bytes; фактичний максимум узгоджується HELLO
CRC = CRC-16/CCITT-FALSE
poly=0x1021, init=0xFFFF, refin=false, refout=false, xorout=0
test vector ASCII "123456789" -> 0x29B1
```

Це справжній поліноміальний CRC, не адитивна checksum із чужого HiRange-протоколу. COBS дає роздільник 0x00 навіть для довільних двійкових даних. Після помилки parser відкидає кадр і знаходить наступний delimiter.

MCU не має виділяти RAM за неперевіреною length: ліміти відомі наперед. Для payload=512 raw займає максимум 522 байти; wire — не більше 526 байтів. Потрібні RX/TX buffers і bounded queue, щоб це вписалось у 8 КіБ RAM поруч із вимірювальними даними.

`request_id` — номер запиту **тільки під час обміну**, не наскрізний ID спрацювання в Flash. Спочатку достатньо одного активного запиту. Відповідь повторює request_id/opcode; її payload починається з коду status. Події kind=3 мають окремо визначений формат і не змішуються з відповідями.

На таймаут читання можна повторити ідемпотентний запит. Для commit/записів повтор із тим самим token/request не має повторно створювати новий запис або стирати дані. Кешувати останній результат зміни стану в межах поточної протокольної сесії.

### Початкові операції

| Операція | Призначення |
|---|---|
| `HELLO` | Model, firmware/protocol version, boot/session, reset cause, capabilities, max payload, layout revisions |
| `GET_STATUS` | CNT, rate, dose, uptime, raw ADC, battery/solar indication, state flags |
| `GET_SETTINGS` | Поточні налаштування та revision |
| `SET_SETTINGS` | Перевірити й атомарно застосувати пакет змін у RAM |
| `COMMIT_SETTINGS` | Зберегти обрану revision до EEPROM, повернути результат |
| `SET_TIME_ANCHOR` | Встановити UNIX anchor з прив’язкою до монотонного часу без очищення логу |
| `GET_LOG_INFO` | Доступні типи логів, обсяги, діапазони, record layout/version |
| `OPEN_SNAPSHOT` | Зафіксувати метадані читання й доступний діапазон |
| `READ_LOG` | Прочитати блок з snapshot + logical offset |
| `CLOSE_SNAPSHOT` | Звільнити стан читання |
| `SUBSCRIBE_STATUS` | Узгоджена частота live-оновлень; для v1 можна замінити GET_STATUS 1/с |
| `REBOOT` / `ENTER_BOOTLOADER` | Окремі явні сервісні операції |

Коди status мінімально: OK, BAD_VERSION, BAD_LENGTH, BAD_CRC/помилка кадру за узгодженою політикою, UNKNOWN_OPCODE, INVALID_VALUE, BUSY, CONFLICT, SNAPSHOT_EXPIRED, STORAGE_ERROR. Пошкоджений CRC кадр за замовчуванням просто відкидається; відповісти BAD_CRC можна лише якщо безпечно встановлена адресація запиту.

Не додавати текстові debug printf у той самий stream поза кадрами. Debug — окремий framed event або окремий режим.

### Реалізований початковий зріз у кастомній прошивці

Firmware має USART1 на PA9/PA10, 115200 8N1, приймання через RX interrupt і обмежену RAM-чергу. Реалізовано COBS + CRC-16/CCITT-FALSE та запити `HELLO`, `GET_STATUS`, `GET_SETTINGS`, `SET_SETTING`, `SET_RTC`, `GET_LOG_INFO` і `GET_LOG_PAGE`; максимальний payload — **64 байти**. Пошкоджені кадри відкидаються без відповіді. Текстових повідомлень у serial stream немає.

`HELLO` response payload (10 байтів): `status:u8 | model_id:u16 | protocol_version:u8 | max_payload:u16 | capabilities:u32`. Наразі `model_id=1` (Geiger-2), `protocol_version=1`, `max_payload=64`, bit 0 capabilities означає підтримку `GET_STATUS`.

`GET_STATUS` response payload (25 байтів): `status:u8 | uptime_seconds:u32 | count_today:u32 | rate_cpm:u32 | dose_nsv:u32 | battery_raw:u16 | solar_raw:u16 | usb_raw:u16 | flags:u16`. `dose_nsv` — накопичена за поточну добу доза в nSv; `flags` bit 0 — HV увімкнено, bit 1 — USB визначено як підключений. Усі багатобайтові значення little-endian. Response має `kind=2` і повторює `request_id` та `opcode` запиту. Status `0` — OK, `1` — невідома/непідтримана операція.

Capability bits: bit 0 — `GET_STATUS`, bit 1 — `GET_SETTINGS`, bit 2 — `SET_SETTING`, bit 3 — `GET_LOG_INFO`, bit 4 — `GET_LOG_PAGE`, bit 5 — `GET_SPI_DUMP_PAGE`, bit 6 — `SET_RTC`.

`SET_RTC` (8) request: `seconds_since_2000:u32` little-endian, interpreted as the device's local wall-clock date/time. The device validates the 2000–2099 range, flushes and cuts off the log timeline, then writes the RTC and marks it set. Response is the one-byte status.

`GET_SETTINGS` request має порожній payload; response: `status:u8 | setting_count:u8 | setting_values[setting_count]`, де індекси значень відповідають стабільним ID налаштувань у `board_stm32l051.c`. ID: `0 LED, 1 CLICKS, 2 SCREEN ALARM, 3 LIGHT ALARM, 4 SOUND ALARM, 5 LED BRIGHT, 6 SCREEN BRIGHT, 7 SCREEN TIMER, 8 LEAD ZERO, 9 UNIT, 10 RATE PREFIX, 11 DOSE PREFIX, 12 RATE ROW 2, 13 USE-SPI, 14 RESET, 15 HV, 16 DOSE ALARM, 17 ALARM STOP, 18 POWER OFF, 19 REBOOT, 20 TONE, 21 LONG PRESS, 22 DOSE ROW 2, 23 DOSE PERIOD`. `RATE ROW 2`, `DOSE ROW 2` та `DOSE PERIOD` мають власне циклічне збереження в EEPROM. Поточна прошивка повертає 24 записи; застосунок приймає старіші відповіді на 21 або 22 записи і показує нові пункти як недоступні. `SET_SETTING` request: `setting_id:u8 | value_index:u8`; response містить лише status. Непідтримуване значення повертає status `2`. `RESET`, `POWER OFF` і `REBOOT` — локальні дії; інші підтримувані параметри, включно з рядками екрана, можна змінювати в застосунку. Під час локального редагування на приладі віддалений запис відхиляється.

`GET_LOG_INFO` має порожній request; response: `status:u8 | use_spi:u8 | minute_count:u16 | hour_count:u16 | day_count:u16 | alert_record_count:u16 | calendar_valid:u8 | calendar_seconds:u32 | spi_size_mb:u8 | spi_ready:u8 | jedec[3] | rtc_status:u8 | clock_source:u8`. Лічильники — фізичні збережені записи. `USE-SPI` визначає доступність вкладок MINUTES/HOURS/ALERTS; DAYS доступний завжди. Кількість у вкладці ALERTS — фізичні snapshots; записи у списку дедуплікуються до епізодів. Хвіст після перших 15 байтів додає діагностичні поля для APP; старі клієнти можуть його ігнорувати.

`GET_LOG_PAGE` request: `type:u8 | offset:u16 | limit:u8`, де type: DAYS=0, MINUTES=1, HOURS=2, ALERTS=3; limit 1–3. Response: `status:u8 | type:u8 | offset:u16 | total:u16 | count:u8 | records[count]`. Максимум три записи на відповідь залишає payload у межах 64 байтів. Для агрегатів запис: `period_start_seconds_since_2000:u32 | dose_pulses:u32 | minimum_cpm:u32 | maximum_cpm:u32`; перший елемент — поточний RAM-агрегат, далі persisted history newest-first. Для алертів: `start_seconds_since_2000:u32 | duration_seconds:u32 | dose_pulses:u32 | maximum_cpm:u32`. Дані передаються сторінками напряму зі сховища; журнал цілком у RAM прошивки не копіюється. Поточний 500 ms буфер локального графіка не вимикається.

`GET_SPI_DUMP_PAGE` (7) request: `offset:u32 | length:u8`, length 1–58. Response: `status:u8 | offset:u32 | length:u8 | data[length]`. Запит читає сирі байти SPI NOR без змін; він відхиляється, якщо `USE-SPI` вимкнений, мікросхема не готова або діапазон виходить за межі її щільності. APP збирає повний образ послідовними читаннями по 58 байтів. FLASH і EEPROM читаються окремо через `Read Memory` ROM bootloader.

Snapshot/generation token поки не передається, тому довгі завантаження під час активного запису можуть побачити зміни кільцевого журналу. Синхронізація часу ще не реалізована. RTS/DTR і фізичний обмін усе ще потребують перевірки на платі.

### Налаштування

Пропозиція payload — TLV:

```text
setting_id:u16 | value_type:u8 | value_length:u16 | value
```

Типи: bool, u8/u16/u32/u64, i32, fixed-point/rational, короткий UTF-8 рядок за потреби. Невідомий ID можна пропустити за length. Семантика кожного ID визначена версією схеми; capabilities дозволяють UI приховувати недоступні опції.

Перед SET надсилати expected_revision, щоб оновлення з додатка не затерло нові зміни, зроблені кнопками. Спочатку перевірити весь пакет, потім застосувати його цілком. ACK повертає нову revision та фактично прийняті значення. Зміна повзунка не має писати EEPROM десятки разів на секунду: apply у RAM, commit після завершення/підтвердження змін.

CRC/версія та дві копії конфігурації або журнал у EEPROM дозволять вибрати останню завершену конфігурацію після обриву живлення. ACK про commit видавати після завершення перевіреного запису.

Поля покривають наш план: одиниці/маска дев’яти варіантів, коефіцієнт, вікна AVG/MAX, індикація, пороги, timeout, дія вимкнення, яскравість, формат чисел, розподіл областей логу. Зміна partition логів повинна мати окремо визначену міграцію/очищення — не стирати статистику приховано звичайним SET.

На дроті передавати CNT та коефіцієнт із чіткими одиницями. Великі накопичені значення — u64; у JS використовувати BigInt або hi/lo, не необмежений Number. Для JSON export BigInt перетворювати на десятковий рядок. Не передавати неоднозначне поле `dose`, яке то CPM, то µSv.

### Статистика та кільцеві логи

`OPEN_SNAPSHOT` повертає session/snapshot ID, тип і версію records, межі читання та покоління кільця. Самі записи імпульсів зберігаються компактними, без повернення до наскрізного per-event ID.

`READ_LOG` містить snapshot + offset + бажаний розмір. Відповідь містить той самий snapshot/offset, фактичну довжину та bytes records. Для блоків вистачає generation/offset у метаданих. Знімок метаданих **не копіює весь лог у RAM**.

Вимірювання й записи продовжуються. Якщо writer встиг перезаписати запитуваний старий сектор, відповісти SNAPSHOT_EXPIRED, а не віддати суміш двох поколінь. Можна короткочасно резервувати діапазон, але тільки з явним лімітом, щоб експорт не зупинив логування.

Браузер зберігає boot/session, snapshot/generation та останній завершений offset для resume. Після reconnect перевіряє, чи цей діапазон ще існує. Передачу завершувати перевіркою очікуваної довжини та, за потреби, підсумкової checksum знімка.

Спочатку достатньо request/response по одному блоку 256…512 байтів. Далі, якщо USB-затримки суттєві, додати обмежене вікно/кредити. Не слати весь мегабайт без backpressure; вкладка може тимчасово перестати читати.

Спочатку завантажувати агрегати для потрібного діапазону графіка, а детальні імпульси — при збільшенні/експорті. Це зменшує і час передачі, і витрати приладу.

## 9. Швидкість передачі

Межа UART 8N1 — 10 біт на byte. Нижче ідеальний час без headers, CRC, ACK, USB latency та Flash-read затримок:

| Baud | Корисна межа, bytes/s | 512 КіБ | 1 МіБ |
|---|---:|---:|---:|
| 115200 | 11 520 | 45,5 с | 91,0 с |
| 230400 | 23 040 | 22,8 с | 45,5 с |
| 460800 | 46 080 | 11,4 с | 22,8 с |

При 8E1 — 11 біт/byte: на 115200 повний 1 МіБ займає не менше приблизно 100,1 с. Наша SPI Flash читається значно швидше; для великого експорту вузьким місцем стане UART/USB-планування.

Для v1 залишити 115200 як відому базу. Після перевірки bridge/UART/IRQ навантаження можна прийняти **одну фіксовану 460800 швидкість для робочого протоколу** у наступному профілі/версії. Потенційна економія часу великого експорту суттєва, але надійність треба перевірити.

Важливе обмеження браузера: команда `SET_BAUD`, після якої host робить close/open, може знову перезапустити прилад і повернути його на початкову швидкість. Тому не будувати v1 на автоматичному «підключилися повільно → переключилися швидко» без окремо перевіреної апаратної послідовності. Заздалегідь відома фіксована швидкість на всю сесію простіша.

## 10. Структура чистого JS додатка

Без обов’язкового build step можна організувати ES modules:

```text
index.html
app.js
serial.js          // один port/reader/writer, reconnect та обмежені черги
protocol.js        // COBS, CRC, frame decoder, запити/відповіді
device.js          // capabilities, status, налаштування
logs.js            // snapshot, resume, декодування записів
storage.js         // IndexedDB, export/import
ui.js              // графіки й елементи керування
bootloader.js      // окремий сервісний режим, за потреби
```

TextEncoder/TextDecoder, Uint8Array, DataView, Streams, Blob і IndexedDB достатні для основної функціональності. COBS/CRC — невеликі JS-функції; WebAssembly або native binary не потрібні. Графіки можна малювати Canvas/SVG; бібліотека графіків за бажанням також може бути суто JS.

Read loop не прив’язувати до вкладки UI. Один parser приймає довільні chunks, виділяє завершені кадри, перевіряє довжину/CRC й маршрутизує їх. Один writer серіалізує вихідні кадри. На великому експорті допустимий Dedicated Worker; не блокувати UI довгими синхронними циклами.

У browser-only версії немає COM3/path доступу як у Node; використовувати port object та getInfo. Не перевідкривати порт при переході «Статистика → Налаштування». При фізичному disconnect очистити pending requests, але зберегти завершені дані й метадані resume.

## 11. Що ще не встановлено

1. Точна модель/ревізія Silicon Labs мосту та його поточна постійна конфігурація.
2. Електрична відповідність RTS/DTR → NRST/BOOT0, інверсії й короткі переходи при open/close.
3. Чому Web Serial залишає пристрій неактивним до close та яка подія запускає його після закриття.
4. Стабільність runtime UART на 230400/460800 та допустимий burst розмір без втрати імпульсів.
5. Стабільний обмін прикладного протоколу через браузер після відкриття порту.

Файли MilerdPort повторно не потрібні. Фізичні тести підключення вже проведені; лишилися міжплатформне порівняння, визначення електричної відповідності ліній та підтвердження стабільного прикладного обміну. Повернутися до них після поточного етапу функціоналу.

Первинні публічні джерела, перевірені 2026-10-21:

- [WebSerial Living Standard](https://serial.spec.whatwg.org/): open, SerialOptions, setSignals, getSignals, secure context.

- [ST AN3155](https://www.st.com/resource/en/application_note/an3155-usart-protocol-used-in-the-stm32-bootloader-stmicroelectronics.pdf): ROM USART sync/ACK, read/write/erase/GO.
- [STM32L051C8](https://www.st.com/en/microcontrollers-microprocessors/stm32l051c8.html): можливості MCU.
