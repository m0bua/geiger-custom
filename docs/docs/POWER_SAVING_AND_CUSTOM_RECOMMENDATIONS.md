# Geiger‑2: енергозбереження стоку та рекомендації для кастому

Дата: 2026-10-20. STM32L051C8T6, оригінальна EN 4.1.17.

## 1. Головне

**Сток не реалізує звичайне вимірювання як «STOP → імпульс → коротка обробка → STOP».** Після автоматичного вимкнення екрана він переходить на MSI приблизно 131 кГц і продовжує виконувати основний цикл. Облік імпульсів та секундні розрахунки працюють через переривання.

Окремий шлях повного вимкнення використовує STOP з low-power regulator і WFI. Однак RTC-тривога та EXTI лишаються дозволеними, а явного циклу повторного STOP немає. Це важлива відмінність між назвою стану в інтерфейсі та фактичним станом ядра.

| Стан стоку | MCU | LCD | Збір імпульсів | Як повертається інтерфейс |
|---|---|---|---|---|
| Активний | PLL, 32 МГц, основний цикл | Працює | EXTI PB6 + RTC | Уже активний |
| Автоматично вимкнений екран | MSI 131 072 Гц, цикл продовжується; WFI у цьому шляху немає | Команда Sleep In `0x10`, PB2=0 | Програмно продовжується; наявність фізичних імпульсів залежить від живлення HV | Кнопки PB9/PA4 або програмна подія від USB |
| Додатковий стан після появи USB | Окремий прапорець; цей шлях сам не відновлює 32 МГц | Встановлює PB2=0 | Обробник PB6 лишається тим самим | Подія кнопки переводить PB2=1 та знімає прапорець |
| Повне вимкнення / низька батарея | Одноразовий виклик STOP/WFI, RAM зберігається | Sleep In, периферійні виходи вимикаються | EXTI PB6 не маскується, але HV у цьому стані не підтверджено | Повний програмний вихід зі STOP реалізований для PB9 |

У таблиці «збір продовжується» означає підтверджену доступність програмного шляху. HEX не показує, яке саме навантаження живлять усі керувальні GPIO, тому не можна гарантувати роботу HV після зміни PB2/PA5 без виміру або схеми.

## 2. Джерело, перевірки та межі висновків

Файл `Port-4.1.17(3).hex`, побайтно ідентичний локальному `Port-4.1.17.hex`.

```text
SHA-256:
89368e9b3d8789d641d0d9756971cea92ea10902ea8feffac604745a0791d6d0
```

Досліджено GPIO/EXTI, RTC, IWDG, обидві конфігурації тактування, автоматичний sleep, повний STOP, кнопкові wake-шляхи та основний цикл збору даних.

Оригінальні Thumb-функції виконані у Unicorn. Перевірено межі таймауту та USB, незмінність sleep-прапорців при імпульсі, збільшення лічильників, кнопкові переходи, конфігурацію RTC Alarm A, SCR/SysTick перед WFI і відмову HAL вимкнути PLL, поки PLL є SYSCLK. Готовність периферії задавалася тестовими прапорцями; частину апаратних операцій перехоплено.

Емулятор не вимірює струм, не моделює HV та реальне пробудження кристала. Конфігурація і переходи коду підтверджені; величину економії та поведінку аналогового живлення треба перевірити на пристрої.

## 3. Коли вимикається екран

### Таймаут

Параметр `uint16_t` за `0x20000010` має початкове значення 30. UI змінює його як 0/10/20/30/40/50/60. Значення 0 вимикає автоматичний таймаут.

RTC IRQ `0x08004920` раз на секунду збільшує `uint16_t idle_seconds` за `0x20000440`. Далі перевіряє:

```c
if (timeout != 0 && idle_seconds > timeout) {
    sleep_request = 1;       // byte 0x20000119
    idle_seconds = 0;
}
```

Порівняння саме `>`, тому з нульового лічильника timeout=30 встановлює запит на 31-му секундному IRQ. Через фазу RTC це приблизно 30…31 с від скидання, плюс час до обробки запиту головним циклом.

Коротка/довга подія кнопки в `0x080031E0` скидає idle_seconds. Там є debounce понад 50 мс та визначення довгого утримання понад 700 мс. Звичайні імпульси трубки **не скидають idle_seconds**. Високий фон сам по собі не утримує екран увімкненим.

### Додаткові умови

Гілка `0x080044FA` дозволяє автоматичне вимкнення екрана, коли:

- у перевірюваних основним циклом станах немає активної операції (`R9 | R5 == 0` у цій гілці);
- сире значення USB/зовнішнього входу **≤1499**.

При USB raw=1500 або вище цей шлях відхиляє сон. Окремий шлях повернення через USB використовує `raw >1500`, тому рівно 1500 має асиметричну обробку. Це підтверджений кодовий поріг, не вимір напруги USB.

### Послідовність входу

`0x08004512–0x0800459A`:

1. Зупиняє відповідну UART-операцію.
2. Змінює TIM21 ARR на 20 та скидає CNT.
3. Скидає sleep_request; встановлює byte `0x2000043E = 1`.
4. Зупиняє PWM/DMA звуку та TIM2, вимикає RGB: PA0/PA1/PA6=HIGH.
5. Встановлює PB8=LOW, тобто вимикає ліхтарик; PB2=LOW.
6. Зберігає поточний номер екрана в `0x20000115`; встановлює `0x20000117 = 1`.
7. Надсилає LCD Sleep In `0x10`, чекає 200 мс.
8. Викликає конфігурацію низької частоти `0x080035AC`.
9. Повертається до основного циклу. **HAL_PWR_EnterSTOPMode тут не викликається.**

PB2 за поведінкою є виходом, пов’язаним з активним станом/екраном, але його фізичне навантаження не встановлено. Не використовувати цю таблицю як доказ, що PB2 є HV-enable.

## 4. Що працює з вимкненим екраном

### Тактування та цикли

`0x080035AC` запитує MSI range 1 — **131 072 Гц**, SYSCLK=MSI, AHB/APB без ділення. RTC продовжує працювати від LSE.

Основний цикл лишається активним. Зокрема:

- освіжає watchdog;
- опитує батарею, USB і сонячний канал через `0x08008FF0`;
- обробляє прапорці, розраховує рівень/дозу й перевіряє живлення;
- пропускає штатну відмальовку, коли `0x20000117 != 0`;
- обробляє EXTI та RTC у перериваннях.

У вимірюванні ADC кожен прохід піднімає PB10, чекає 5 мс, калібрує ADC, читає три канали, опускає PB10 і чекає ще 1 мс. Частота опитування визначається тривалістю основного циклу, а не окремим рідким таймером. Це створює зайву роботу для задачі, де батарею зазвичай не потрібно читати на кожному проході.

TIM21 теж не переводиться в рідкісний режим: PSC=239 і ARR=20 при 131 072 Гц дають приблизно **38,45 мс**, або 26,0 IRQ/с. В активному стані ARR=4999 при 32 МГц дає 37,5 мс. Отже, зміна ARR приблизно зберігає частоту обробника індикації після зниження частоти CPU.

### Облік імпульсу

PB6 налаштований як EXTI falling edge. `0x0800349A–0x080034BE` незалежно від screen-off/STOP-прапорців збільшує:

| RAM | Тип | Призначення |
|---|---|---|
| `0x20000450` | uint32_t | Очікування звукової/світлової індикації |
| `0x20000454` | uint16_t | Лічильник поточної секунди |
| `0x20000456` | uint16_t | Лічильник поточного періоду |
| `0x2000011C + 2*index` | uint16_t | Поточна комірка секундного кільця |

Обробник імпульсу не вмикає LCD, не викликає PLL-конфігурацію та не скидає таймаут. У режимі екран-off ядро вже виконує код на MSI, тому це звичайне переривання працюючого процесора.

Звук у штатному періодичному обробнику приглушений прапорцем `0x2000043E`. Під час самого входу RGB вимикається, але його періодична гілка перевіряє окремий LED-enable; screen-off прапорець не є загальним блокуванням усіх індикацій.

### Секундне агрегування

RTC IRQ `0x08004920`:

1. Оновлює секундні та idle-лічильники, освіжає IWDG.
2. Пересуває індекс секундного кільця, обчислює суму за вікно `W` секунд.
3. Очищає комірку, в яку писатимуться нові імпульси.
4. Раз на `W` секунд ставить прапорець оновлення дози та копіює лічильник періоду.

`W` початково 60, зберігається за `0x20000084`. Подальші CPM, µSv/h і доза обчислюються основним циклом. Вони не потребують увімкненого LCD.

Для кастому краще накопичувати дозу безпосередньо з точного числа імпульсів. У стоку головний цикл використовує булевий прапорець і поточну суму ковзного вікна; при затримках основного циклу це гірше за атомарний лічильник накопичених подій. Кілька невиконаних інтервалів можуть злитися в один прапорець.

Історія цього вимірювального шляху тримається в RAM; поподійного запису до SPI тут немає. Це не схема нашого майбутнього кільцевого логу.

## 5. Як повертається екран

Кнопкові EXTI: PA4 і PB9. В обох випадках `0x080034C2` при `screen_off != 0`:

- повертає 32 МГц через `0x08003378`;
- встановлює PA14=HIGH, PB8=LOW, PB2=HIGH;
- скидає screen_off, audio-suppression, sleep_request та idle_seconds;
- відновлює номер екрана із збереженого byte;
- встановлює `0x20000114=1` як запит відновлення LCD.

Головний цикл потім виконує `0x080039D0`: підготовку SPI Flash, запуск TIM21, LCD Sleep Out `0x11`, затримку 200 мс, повернення TIM21 ARR=4999 і запуск TIM2.

USB при screen_off та raw>1500 генерує програмний виклик тієї ж кнопкової функції з mask=0x10 (`0x080039BC`). Це **опитування ADC у головному циклі**, не окрема доведена апаратна USB wake-line.

Є також шлях `0x0800459E`: після появи USB він може поставити PB2=LOW і byte `0x20000109=1`. Наступна подія кнопки в `0x08003520` повертає PB2=HIGH та знімає цей прапорець. Цей фрагмент сам не відновлює PLL; не варто копіювати його в кастом без єдиної явної моделі станів.

## 6. Повне вимкнення — що робить STOP

### Умови виклику

Функція `0x08003648` викликається:

- при штатному запиті вимкнення: довга подія PB9, основний екран/дозволені сторінки 1…6, нормальний power mode=3;
- при низькому battery raw: mode 1 для 0…1229, mode 2 для 1230…1295;
- при старті, якщо power mode не нормальний. Mode 0 має окремий шлях сигналізації й не є тим самим підтвердженим STOP-вимкненням.

Для mode 3 є додатковий екран/світлова послідовність. Перед спільною частиною вимкнення код зупиняє TIM21 IRQ, UART/DMA і звуковий PWM, обнуляє pending-індикацію, ставить PA5=LOW.

Спільна частина:

```text
PB2 = LOW
PA0 / PA1 / PA6 = HIGH
PB8 = LOW
LCD Sleep In 0x10, delay 200 ms
низькочастотна конфігурація
PWR ULP = 1, FWU = 0
SysTick TICKINT = 0
stop_flag (0x20000118) = 1
HAL_PWR_EnterSTOPMode(LOWPOWERREGULATOR_ON, WFI)
```

Виклик STOP за `0x08003714`; WFI за `0x080059C6`. Це STOP із збереженням RAM, а не апаратне від’єднання акумулятора. PA5 та PB2 перемикаються, але конкретні підключені до них навантаження за HEX не встановлені.

### Які джерела можуть вивести ядро зі STOP

| Джерело | Що залишає код | Що робить програмний обробник |
|---|---|---|
| PB9 | EXTI дозволений | При stop_flag=1 відновлює тактування й активний стан |
| PA4 | EXTI дозволений | Окремого повного відновлення при самому stop_flag немає |
| PB6 | EXTI дозволений | Інкрементує імпульсні лічильники; не знімає stop_flag |
| RTC Alarm A | Тривога, її IRQ та EXTI17 залишаються дозволеними | Виконує звичайну секундну логіку, освіжає IWDG; не відновлює повний активний стан |
| IWDG | Запущений і не вимикається | За простроченням викликає reset, це не нормальне продовження після WFI |

Для PB6 умова фізичного пробудження — реальний фронт на ніжці. Якщо силовий каскад вимкнув HV, імпульсів від трубки не буде. Доведено, що EXTI не замаскований; роботу HV у цьому стані не доведено.

### Важлива проблема: один WFI та активна RTC

RTC налаштована від LSE, prediv A=127 / S=255. Alarm A має mask `0x80808080`, тобто календарні поля замасковані; використовується секундне переривання. Після виконання оригінального Alarm init:

```text
RTC_CR = 0x00001100      // ALRAE + ALRAIE
RTC_ALRMAR = 0x81808080
EXTI_IMR bit 17 = 1
RTC_IRQn = 2, вектор -> 0x08004921
```

Шлях вимкнення не відключає ці біти й не вимикає NVIC RTC. Він також не маскує EXTI PB6/PA4/PB9. Перед WFI отримано SCR=0x4, тобто SLEEPDEEP=1, **SLEEPONEXIT=0**.

Після будь-якого дозволеного IRQ WFI завершується. HAL прибирає SLEEPDEEP і повертається з функції; у `0x08003648` немає циклу повторного засинання. У головному циклі також немає загального захисту «stop_flag=1 → знову STOP». Для нормальної батареї повернення з ручного вимкнення йде далі через `0x08003BA0`.

**Висновок з коду:** логічний прапорець «вимкнено» може лишатися встановленим після фізичного пробудження ядра. RTC або PB6 можуть вивести MCU зі STOP без штатного повного відновлення, і програма продовжить виконання з вимкненим SysTick IRQ. Можливі зайва активність або зависання в очікуванні HAL_Delay. Це конкретний ризик реалізації, а не доведений виміром єдиний чинник розряду пристрою.

За низької батареї основний цикл може знову дійти до low-battery вимкнення. Це не замінює правильного контрольованого повторного STOP для ручного OFF.

## 7. Друга проблема: порядок вимкнення PLL

В `0x080035AC` послідовність така:

1. `HAL_RCC_OscConfig`: увімкнути MSI, PLLState=OFF.
2. `HAL_RCC_ClockConfig`: переключити SYSCLK з PLL на MSI.

Але поки SYSCLK використовує PLL, оригінальний HAL за `0x08005ECA/0x08005F6E` відхиляє PLL_OFF з `HAL_ERROR`. Результат виклику ігнорується. При цьому MSI вже може бути підготовлений, і наступний виклик переключає SYSCLK на MSI. **CPU сповільнюється, але PLL у режимі екран-off може лишитися увімкненим.** HSI16 також явно не вимикається цим запитом.

Це перевірено оригінальним HAL: для початкового SYSCLK=PLL і цього запиту він повернув 1, а PLLON лишився встановленим. Це не припущення за типовою HAL-поведінкою.

Правильний порядок у кастомі:

```text
увімкнути MSI та дочекатися ready
переключити SYSCLK на MSI та перевірити SWS
вимкнути PLL
вимкнути HSI16, якщо він не потрібний активній периферії
узгодити SystemCoreClock і timebase
```

Потрібно перевіряти результати кожного HAL-виклику. Залишати HSI16 дозволеним, якщо його потребує поточне ADC/UART-тактування; спочатку завершити або переналаштувати цю периферію.

## 8. Watchdog

`0x080031B0` запускає IWDG. Фактичні значення:

```text
Prescaler = 6 -> /256
Reload = 625
Window = 4095 -> вікно не обмежує часті refresh
```

Таймаут дорівнює `(625+1)*256/fLSI`: приблизно 4,3 с при номінальних 37 кГц; реальний LSI має розкид. Константа 4095 тут **window**, а не reload.

IWDG refresh стоїть і в основному циклі, і в секундному RTC IRQ. Тому RTC може продовжувати годувати watchdog навіть тоді, коли основний код застряг. Для кастому це послаблює перевірку працездатності застосунку.

Не можна планувати необмежений STOP, просто переставши годувати вже запущений IWDG. Потрібен контрольований період пробуджень або інша узгоджена політика watchdog. Поточні option bytes пристрою цим HEX не встановлені.

## 9. Рекомендована схема для кастому

Нижче — рекомендації, а не опис уже реалізованого кастому.

### 9.1. Явно розділити режими

| Режим | Датчик / HV | LCD | Події, які треба обробляти |
|---|---|---|---|
| Екран увімкнений | Увімкнений | Активний | Імпульси, RTC, кнопки, UART, таймери UI/звуку |
| Вимірювання з вимкненим екраном | Увімкнений | Sleep, підсвітка off | Імпульси, RTC, кнопки, заплановані операції логування |
| Датчик вимкнений | Вимкнути лише після встановлення реального HV-enable | За налаштуванням | Кнопки, годинник, зв’язок; позначати розрив вимірювання |
| Повне програмне OFF | Підтверджені навантаження вимкнені | Sleep | Дозволена кнопка увімкнення та мінімально необхідне обслуговування |

Параметр дії кнопки вимкнення з нашого плану має вибирати один із цих станів. Джерело пробудження та стан інтерфейсу — різні речі: імпульс може коротко розбудити MCU для обліку, залишивши LCD вимкненим.

### 9.2. Сон між роботами замість постійного циклу

Для першої надійної версії можна використати звичайний CPU Sleep/WFI між подіями, а потім перейти до STOP після перевірки часу відновлення та обліку імпульсів. Sleep простіший: робочі таймери й більшість тактування зберігаються. STOP дає більшу потенційну економію MCU, але потребує явного відновлення clocks і правильного часу.

Цільовий цикл вимірювання з вимкненим екраном:

```text
сон -> PB6 IRQ -> лічильник + timestamp у RAM -> обробка потрібних задач -> сон
сон -> RTC IRQ -> секундний bucket / агрегат / watchdog -> сон
сон -> кнопка -> повний активний режим, LCD wake
```

Захистити перевірку черги та вхід у WFI від гонки «імпульс прийшов після перевірки, але перед засинанням». Для Cortex-M0+ це робиться короткою критичною секцією з повторною перевіркою pending та коректним WFI/масками, або перевіреною WFE-схемою. Одного `if (!pending) WFI` без такої перевірки недостатньо для надійного планувальника.

Рішення «знову спати чи залишитись активним» має бути в одному місці основного циклу. Після кожного пробудження він знову оцінює стан і дедлайни. Не повторювати стокову схему одного WFI всередині функції OFF.

#### Перший крок у кастомі

У `src/main.c` після обробки чергової порції задач додано звичайний `WFI`.
Поки дисплей активний або має незавершену роботу, SysTick лишається 1 ms.
Після вимкнення підсвітки та спорожнення черги LCD він переходить на 10 ms;
після пробудження для кнопки/екрана знову повертається на 1 ms. Ядро також
негайно реагує на IRQ детектора, RTC, DMA та кнопок. Це скорочує періодичні
пробудження у спокої вдесятеро, не змінюючи частоту ядра й не входячи в STOP.
ADC розділено за каналами: SOLAR читається кожні 300 ms (близько 3,3 рази/с) лише при
ввімкненій підсвітці; батарея — раз на 30 секунд при активному екрані, у
простою — раз на 10 хвилин, або раз на 30 секунд, якщо показане чи очікуване
значення нижче 3%. USB читається разом із батареєю лише при активному екрані.
Перше вимірювання батареї відбувається одразу після старту; її відсоток має
окрему 90-секундну стабілізацію. Часте опитування SOLAR забезпечує реакцію
автояскравості до 300 ms, а батарейний канал не опитується на кожному SOLAR
вимірі.
Після кожної серії ADC вимикається через ADDIS, вимикається його внутрішній
регулятор і закривається тактування ADC1. Калібрувальний коефіцієнт лишається
збереженим при ADEN=0; при наступному вимірі ADC повторно запускається та
очікує ADRDY перед конверсіями.
Коли RGB-канали не світяться, TIM2/TIM22 зупиняються, а їхні APB clock gates
вимикаються. TIM2 лишається активним під час RGB червоного/зеленого або звуку;
TIM22 — лише під час синього каналу. Генератори PWM запускаються при ненульовій
яскравості та зупиняються після вимкнення відповідних виходів.

Це програмна оптимізація, її фактичний вплив на струм треба виміряти на платі.
Наступний рівень — прибрати періодичний SysTick із режиму бездіяльності та
спланувати пробудження через RTC/LPTIM. Перед STOP потрібно окремо реалізувати й
перевірити відновлення тактування, SysTick, SPI/LCD, ADC та повторний сон після
службових IRQ; поточний WFI цього не робить.

Послідовність керування ADC та збереження калібрування при ADEN=0 відповідають
[RM0377, розділ 13.3](https://www.st.com/resource/en/reference_manual/rm0377-ultralowpower-stm32l0x1-advanced-armbased-32bit-mcus-stmicroelectronics.pdf).

### 9.3. Облік і доза — з імпульсів

- У PB6 IRQ інкрементувати 32- або 64-бітний загальний CNT та поточний секундний bucket; для 64 біт на Cortex-M0+ забезпечити атомарне читання.
- Дозу виводити із загального CNT та коефіцієнта. Для різниць у часі брати snapshot CNT, а не суму ковзного вікна з булевим прапорцем.
- Хвилинні/годинні агрегати формувати з точних різниць CNT. Для MIN/MAX/AVG чітко визначити вікно оцінки рівня.
- При відкладеній обробці зберігати кількість пропущених секунд/інтервалів або використовувати різницю монотонного часу. Булевий прапорець не зберігає число пропущених tick.
- При високому потоці дозволено обмежити частоту звуку/LED, але не частоту обліку імпульсів.

Після переходу до STOP треба навантажувально перевірити PB6: EXTI pending — це прапорець, а не черга фронтів. Два фронти до очищення одного pending можуть злитися. Сон із дуже повільною обробкою не повинен обмежити діапазон дозиметра.

### 9.4. Часові мітки для нашого логу

SysTick і звичайний TIM2/TIM21 не є безперервним джерелом часу у STOP. `HAL_GetTick()` не можна використовувати як точний час між подіями через глибокий сон.

Стоковий RTC має sync predivider=255: поточний subsecond крок приблизно **3,90625 мс**. Для нашого варіанта 2 байти на інтервал до 10 с крок буде приблизно **153 мкс** після резервування спеціальних кодів. Штатної subsecond-конфігурації недостатньо для такої точності.

Варіанти для кастому:

- RTC на LSE з іншим поділом, наприклад async=0, sync=32767: теоретичний крок SSR — 30,5 мкс. Оцінити додаткове споживання RTC та правильно читати секунди/subseconds на межі переносу.
- LPTIM із незалежним низькочастотним тактуванням, якщо вибрана конфігурація працює у потрібному STOP-режимі; обробляти переповнення та зберігати довгу шкалу часу.

Для нашої моделі логування зручно залишити апаратну шкалу монотонною, а UNIX-час задавати окремим anchor/offset. Синхронізація часу з додатка тоді не змінює вже виміряні інтервали між імпульсами.

### 9.5. Рідше ADC, пакети у SPI

Початкові інтервали для перевірки: батарея раз на 10…30 с, сонячний вхід раз на 1…5 с, якщо він потрібний для автояскравості. Це стартові параметри кастому, їх потрібно підібрати за вимірами. USB можна опитувати разом із джерелами живлення; апаратний wake використовувати лише після підтвердження відповідного підключення.

Зберегти підтверджену послідовність PB10/HAL ADC для коректних читань, але запускати її за дедлайном. Калібрування ADC виконувати тоді, коли це потрібно після init/відновлення/зміни конфігурації згідно з вимогами ADC, а не безумовно на кожному проході.

Імпульси накопичувати в RAM і писати до SPI пакетами з обмеженим часом очікування або при заповненні буфера. Курсор логу тримати в RAM; сканувати/відновлювати його при старті. Перед стиранням мати заздалегідь підготовлений сектор. Довге SPI busy-очікування не повинно маскувати PB6.

Поки Flash програмує/стирає, вона має живитися. Після завершення операцій можна використовувати її режим deep power-down, якщо він увімкнений у драйвері для точного встановленого чипа; дотримуватись часу виходу перед наступним доступом. Не вимикати її живлення або не переводити у сон посеред незавершеної операції.

За пакетного запису раптове зникнення живлення може втратити останній RAM-буфер. Задати допустиме вікно втрати даних, а записи Flash зробити відновлюваними після незавершеного program: ознака завершення/CRC, заголовки секторів, послідовність поколінь. Самого FF-курсора недостатньо для всіх випадків обриву запису й другого кола.

### 9.6. Окрема політика для звуку та світла

Стоковий клік має вікно приблизно 37,5 мс. Для економії можна зробити коротший клік і перевірити його чутність на цьому випромінювачі. Наприклад 2…5 мс — лише кандидат для експерименту; звук зміниться. Частоту 4,47 кГц та заповнення 16% лишити початковими параметрами.

Коли потрібний звук, звичайний TIM2 PWM не працюватиме у STOP: на час кліку залишатися у Run/Sleep, потім вимкнути PWM і повернутися до STOP. Не будити LCD заради кліку.

RGB обмежувати за тривалістю та частотою. Ліхтарик PB8 вимикати за обраною користувачем політикою. LCD оновлювати за зміною даних/обмеженим FPS і невеликими областями; це зменшує час роботи CPU/SPI при активному екрані.

### 9.7. Watchdog і низька батарея

Watchdog годувати після підтвердження, що потрібні задачі живі. RTC IRQ може встановлювати запит/контрольний tick, але не має безумовно приховувати зависання основного коду. Водночас цикл STOP повинен вчасно обслуговувати IWDG, якщо він запущений.

Для батареї додати фільтрацію, підтвердження кількома вимірами та гістерезис повернення. На критичному рівні завершити дозволений короткий запис, припинити нові erase, вимкнути підтверджені навантаження та перейти у контрольований OFF. Пороги Flash-запису прив’язати до гарантованого живлення пам’яті/стабілізатора, а не лише до красивого відсотка.

Стокові ADC-пороги не є універсальними напругами. Зокрема, на поточному кастомі повідомлялось raw близько 2050; перед використанням порогів стоку перевірити 12-бітну конфігурацію, канал, PB10, опорну напругу та фактичну напругу батареї. Не підганяти коефіцієнти під неправильний ADC.

### 9.8. Силова частина може визначати весь результат

Економія MCU не гарантує такого самого зниження споживання всього дозиметра. Окремо виміряти HV, LCD/підсвітку, зарядний/сонячний тракт і SPI Flash. GPIO enable навантажень установити за схемою/виміром. Не вимикати HV між імпульсами для економії: під час набору високої напруги трубка не вимірюватиме коректно.

Також перевірити відсутність підживлення через SPI/UART/SWD GPIO до знеструмлених вузлів. Для невикористаних входів обрати визначений стан, але не переводити PB6/кнопкові wake-входи в analog. Вимірювати sleep-струм без активної SWD-сесії та підключених навантажень, які можуть утримувати режим debug або підживлювати плату.

## 10. Що перевірити на кастомі в першу чергу

| Перевірка | Навіщо |
|---|---|
| Струм із LCD on, LCD sleep, MCU Sleep, MCU STOP, повний OFF | Відокремити витрати MCU від периферії |

Найбільший очікуваний виграш у прошивці: **прибрати активний цикл при вимкненому екрані, правильно вимикати clocks, рідше читати ADC та надійно повертатися у сон після кожної службової події**. Точний виграш у мА/годинах автономності визначається вимірюваннями.

## 12. Кастомна прошивка: screen-off clock і польове порівняння

У прошивці кастому `src/main.c` / `src/board_stm32l051.c` додано screen-off тактування за зразком стоку: при погашеному екрані, спорожнілій LCD-черзі та відсутності сигналізації SYSCLK переходить на MSI 131.072 кГц, після чого вимикаються PLL та HSI16. Перед кнопковим пробудженням, ADC-виміром і сигналізацією частота повертається до PLL 32 МГц. SysTick перебудовується під поточну частоту, період опитування в простої лишається 10 мс.

Під час пробудження підсвітка спершу стартує на 1%, а після першого актуального виміру ADC застосовується задана або автоматична яскравість, щоб уникнути короткого спалаху зі старим сонячним показом.

Імпульс трубки тримає повну частоту щонайменше 500 мс, що зберігає швидку LED/звукову індикацію. Кнопки PA4/PB9 налаштовані на EXTI за обома фронтами, а поточний GPIO-рівень перевіряється в уже наявному 10-мс циклі як резерв. Пробудження одразу повертає 32 МГц і 1-мс SysTick перед увімкненням підсвітки. EXTI зберігає, яка саме кнопка розбудила пристрій, навіть якщо тап уже завершився.

`src/button_input.c` веде стан кожної кнопки за `board_millis`: debounce 20 мс, довге натискання 800 мс. Перший клік після погашеного екрана лише будить його; стан кнопки приглушується до 20 мс стабільного відпускання, без очікування окремої UP-події. У `main.c` прибрано додаткові маски приглушення й лічильники відпускання. Після затримки цикл виконує одну актуальну вибірку (`next_sample = now`), не відтворює пропущені опитування: кількість викликів більше не може перетворити коротке натискання на довге.

Нові LCD-перемальовування відкладаються при погашеній підсвітці; уже розпочатий обмін завершується. Pending-перемальовування враховано в `board_display_busy()` при активному екрані, а перед LCD-сервісом та секундними 64-бітними обчисленнями повертаються 32 МГц. Це усуває тривалу растеризацію на MSI, яка затримувала обробку кнопок. Між службовими інтервалами зберігаються MSI, 10-мс SysTick і WFI; STOP для звичайного вимірювання не використовується.

Перевірка без плати: `python tools/test_buttons.py --firmware .pio/build/geiger2/firmware.elf` після збірки. Unicorn установлюється локально командою `python -m pip install --target .pio/testdeps unicorn`. Виконуються 15 сценаріїв реального Cortex-M0+ коду кнопок: короткі/довгі кліки, затримки циклу, багато викликів без спливання часу, брязкіт, пробудження після завершеного тапу, незалежність кнопок та переповнення часу. Додатково зібрана прошивка перевіряється через її EXTI/GPIO-адаптер для обох кнопок і одночасного натискання.
