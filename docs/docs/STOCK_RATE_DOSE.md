# Mira Safety Geiger-2 / Milerd HiStand: підрахунок рівня, дози та кольорові пороги стокової прошивки

Дата аналізу: 2026-10-19. Джерело: наданий `Port-4.1.17(3).hex`. Аналіз для STM32L051C8T6, трубки SBM-20-1; заявлена користувачем робоча напруга трубки — 400 V. Напруга HV не входить як змінна у відновлені формули.

Це розбір алгоритмів саме оригінального HEX. Поточний прототип використовує
60-секундне ковзне вікно й показує швидкість та накопичену дозу; його
компонування й обмеження описані в [LCD_AND_DISPLAY](LCD_AND_DISPLAY.md).

## 0. Як саме формується число на головному екрані

Цей розділ додано після уточнення запиту. Тут розглянуто час оновлення, порядок перерахунку та округлення готового показу. Функції форматування також перевірені виконанням із HEX: отримано саме рядки, які передаються renderer’у.

### 0.1. Імпульси → секундні комірки → ковзна сума

Кожний прийнятий імпульс одразу збільшує **поточну секундну комірку**. Наприклад, протягом однієї секунди прийшли 3 імпульси — її комірка міститиме 3. На кожному імпульсі нове число µSv/h або CPM не обчислюється.

Раз на секунду RTC IRQ формує `N` — суму комірок за останні `W` завершених секунд. `W` — налаштування 10–60 секунд, початково 60. Потім комірка, яка вийшла з вікна, очищається для наступного секундного інтервалу.

Таким чином, при `W = 60` щосекунди маємо нову суму **за останні 60 секунд**. Це не окремі неперекривні хвилини: на кожному секундному кроці нова секунда входить у вікно, а стара виходить.

За звичайної роботи:

```text
N_нове = N_попереднє + імпульси_нової_секунди − імпульси_старої_секунди
```

Сам сток для цього щоразу заново складає весь масив. Якщо нових імпульсів не було, `N` може зменшитися через вихід старих імпульсів із вікна. Якщо кількість нових і тих, що вийшли, однакова, `N` не зміниться.

Окремий секундний лічильник у RAM є, але він не використовується як округлений CPS для розрахунку рівня. Жодного округлення частоти кожної окремої секунди перед складанням немає.

### 0.2. Чи спочатку CPM, а потім Sv?

Після секундного підсумовування з одного `N` формуються **дві гілки**:

```text
CPM_неокруглений = N × 60 / W
µSv/h           = N × 3600 / W × 0.000111
```

У машинному коді спочатку утворюється еквівалент CPH (`N × (3600 / W)`), після чого:

- для µSv/h він множиться на `K`;
- для CPM він ділиться на 60 і перетворюється на ціле.

**Показ µSv/h не обчислюється з уже обрізаного цілого CPM.** Тому дробова частина частоти, можлива при `W = 40` чи `50`, впливає на µSv/h, хоча в показі CPM вона губиться.

Наприклад, `W = 50 s`, `N = 113`:

```text
Частота до обрізання: 135.6 CPM
CPM на екрані:        0135
Внутрішній рівень:    0.903096 µSv/h
Рядок рівня:          0.90
```

Пороги кольору використовують `0.903096`, тож у цьому прикладі значок уже червоний, хоча число після округлення — `0.90`.

### 0.3. Коли саме оновлюється число

| Подія / етап | Коли виконується |
| --- | --- |
| Збільшення секундної комірки | На кожний імпульс, у EXTI callback |
| Оновлення `N` | Раз на секунду, у RTC IRQ |
| Обчислення внутрішнього рівня та CPM | У проходах основного циклу з останнього доступного `N` |
| Форматування та передавання рядка на активний головний екран | У проходах UI основного циклу |
| Додавання накопиченої дози | Після прапорця завершення періоду, приблизно раз на `W` секунд |

Числовий renderer викликається через `main → 0x0800ABAC → 0x0800AB28 → 0x0800A84C`. Окремого таймера «оновлювати цифри раз на W секунд» у цьому шляху немає. Повторний виклик UI може знову малювати те саме число.

Треба розрізняти частоту зміни **джерела даних** і частоту перемальовування LCD. Джерело `N` змінюється за секундними IRQ; швидкість проходження UI залежить від роботи основного циклу, передачі графіки та інших дій. Якщо main зайнятий, екран отримає нове значення пізніше або пропустить проміжні значення.

Для імпульсу між двома секундними IRQ затримка його врахування в числовому показі — до наступного тіку, плюс обробка main/UI. Одразу на імпульс реагує лічильна гілка, а не формування нового текстового числа.

### 0.4. Приклад із одним додатковим спрацюванням

Уже заповнене 60-секундне вікно містить 23 імпульси. У комірці, яка зараз вийде з вікна, імпульсів немає.

| Момент | Поточна сума `N`, доступна формулі | Внутрішній рівень | Число на екрані µSv/h |
| --- | --- | --- | --- |
| Перед новим імпульсом | 23 | 0.15318 | `0.15` |
| Імпульс уже прийшов, наступного RTC IRQ ще не було | 23 | 0.15318 | `0.15` |
| Наступний секундний IRQ та обробка UI | 24 | 0.15984 | `0.16` |

Якби зі старою секундою одночасно вийшов один імпульс, сума залишилася б 23. Тоді нове спрацювання не змінило б показу рівня.

Цю послідовність відтворено послідовним виконанням оригінального імпульсного callback, RTC IRQ, блоку формули та числового UI.

### 0.5. Як округлюється CPM

Після обчислення частоти у `double` дробова частина CPM **відкидається**. Для невід’ємних значень це еквівалент `floor`. Отримане ціле зберігається в 16 бітах.

Формат рядка — **`%04d`**, тобто мінімум чотири цифри з початковими нулями:

```text
23 CPM    → "0023"
135.6 CPM → "0135"
```

Результат не округлюється до найближчого CPM. Перед перерахунком у µSv/h це обрізання не застосовується.

### 0.6. Як округлюється µSv/h

Шлях числового значення:

```text
внутрішній рівень double → кеш float → formatter 0x0800A390 → рядок
```

У типовому діапазоні до 10 formatter додає приблизно `0.005`, виділяє цілу частину та дві десяткові цифри. Це дає округлення до сотих з особливостями binary32 на граничних значеннях. Форматування повторюється під час UI, а не після накопичення певного числа імпульсів чи завершення всього вікна.

Перевірені кінцеві рядки для `W = 60`:

| Імпульсів за останні 60 s | Внутрішній рівень, µSv/h | Рядок |
| --- | --- | --- |
| 21 | 0.13986 | `0.14` |
| 22 | 0.14652 | `0.15` |
| 23 | 0.15318 | `0.15` |
| 24 | 0.15984 | `0.16` |
| 25 | 0.16650 | `0.17` |
| 150 | 0.99900 | `1.00` |

Тому два різних внутрішніх значення можуть показуватися однаково. Наприклад, перехід 22 → 23 CPM змінює справжній рівень, але обидва значення після форматування дають `0.15`.

Приблизно в діапазоні 10–100 formatter залишає **одну цифру після крапки** через обрізання рядка до чотирьох символів. Це не повноцінне математичне округлення до десятих: спочатку застосовується поправка `+0.005`, а потім губиться остання цифра. Виконання оригінальної функції дало:

```text
0.15318 → "0.15"
0.15984 → "0.16"
0.999   → "1.00"
9.995   → "10.0"
10.05   → "10.0"
12.345  → "12.3"
15.318  → "15.3"
99.99   → "99.9"
100.0   → "100.00"
```

Останній рядок показує, що поведінка formatter поза діапазоном 10–100 відрізняється; таблиця описує сформований текст, не гарантує його коректне розміщення на LCD.

Для µR/h числовий UI спочатку множить рівень на 100, а далі застосовує той самий formatter. Наприклад, `23 CPM → 0.15318 µSv/h → 15.318 µR/h → "15.3"`.

### 0.7. Як W впливає на стрибки показу

Кожний додатковий імпульс у вікні змінює частоту та рівень на:

| W | Крок істинного CPM | Крок внутрішнього µSv/h |
| --- | --- | --- |
| 10 s | 6 | 0.03996 |
| 20 s | 3 | 0.01998 |
| 30 s | 2 | 0.01332 |
| 40 s | 1.5 | 0.00999 |
| 50 s | 1.2 | 0.007992 |
| 60 s | 1 | 0.00666 |

Менше вікно швидше реагує на зміну інтенсивності, але при малих частотах показ стрибає сильніше. Більше вікно згладжує результат через більшу кількість врахованих імпульсів. Частота надходження нової суми при цьому залишається секундною.

На старті знаменник уже дорівнює повному W, хоча комірки ще не заповнені. Початковий показ тому занижений відносно оцінки за реально минулий час і поступово заповнюється протягом W секунд.

### 0.8. Чому при нулі може залишитися попереднє число

Є окреме правило кешу числового показу: Sv/R оновлюється лише при внутрішньому рівні `>= 0.01 µSv/h`, CPM — лише при ненульовому CPM. Якщо умова не виконана, UI може повторно показувати старе кешоване число.

Наприклад, для `W = 60` один імпульс дає `0.00666 µSv/h`. Сам formatter здатний перетворити це на `0.01`, але числовий UI може взагалі не передати нове значення formatter’у через перевірку `>= 0.01`. Це різні етапи.

Це утримання попереднього показу, а не додаткове часове усереднення, не корекція фону і не перерахунок дози з показаного на екрані округленого числа.

## 1. Основні результати

У прошивці знайдено й перевірено виконанням оригінального машинного коду:

- **Коефіцієнт дози `K = 0.000111 µSv / імпульс`.** У коді це IEEE-754 `double`, початкове значення береться з внутрішнього Flash.
- **Рівень: `rate_µSv_h = counts_in_window × (3600 / window_seconds) × K`.** Для доступних у меню вікон ділення `3600 / W` ціле й точне.
- Еквівалентні коефіцієнти: **`0.00666 µSv/h на CPM`**, **`0.3996 µSv/h на CPS`**.
- За замовчуванням `W = 60 s`; меню пропонує `10, 20, 30, 40, 50, 60 s`.
- Рівень визначається прямокутним ковзним вікном із секундних лічильників. Нову суму ISR формує щосекунди.
- Доза оновлюється в основному циклі приблизно раз на `W` секунд: **`dose += counts_in_window × K`**. Окремого додавання дози на кожний імпульс у цьому ланцюгу немає.
- Поточна накопичена доза у стоку прив’язана до поточного дня: під час обробки зміни дня вона обнуляється, а для історії використовуються масиви добових значень у RAM.
- **Зелений: `rate < 0.4`; жовтий: `0.4 ≤ rate ≤ 0.9`; червоний: `rate > 0.9 µSv/h`.** Для LED та екранного значка межі однакові.

Пороги порівнюються з внутрішнім неокругленим рівнем у `µSv/h`. Перемикання одиниць на CPM або µR/h не змінює порогів.

## 4. Приймання імпульсів трубки

### 4.1. Вхід

У `0x08002ECA–0x08002EDA` передається конфігурація GPIO:

```c
port = GPIOB;                  // 0x50000400
pin  = 0x0040;                // PB6
mode = 0x00210000;            // EXTI, falling edge
pull = 1;                     // pull-up
```

Обробник EXTI перевіряє pending-біт 6, очищає його та викликає `0x0800341C(0x0040)`. Гілка PB6 починається на `0x0800349A`.

### 4.2. Що змінюється на кожне спрацювання

Еквівалентний псевдокод цієї гілки:

```c
pending_indication++;         // uint32, 0x20000450
pulses_this_second++;         // uint16, 0x20000454
pulses_this_period++;         // uint16, 0x20000456
second_bins[bin_index]++;     // uint16[60], 0x2000011C
```

`bin_index` — `uint8` за адресою `0x20000458`.

У цій гілці немає переведення в Sv/R, обчислення інтервалу між імпульсами, корекції мертвого часу або віднімання природного фону. Відновлений алгоритм рахує прийняті цифрові імпульси. Те, які фізичні імпульси доходять до PB6, залежить від трубки та аналогової частини.

## 5. Секундний буфер і усереднення рівня

### 5.1. Часова база

RTC ініціалізується з prescaler `127` та `255`; налаштування alarm маскує календарні поля (`0x80808080`), утворюючи повторюваний секундний alarm. Вектор RTC вказує на `0x08004920`.

Нижче `W` означає тривалість вікна в секундах. Початкове значення `60` копіюється з Flash `0x0800FD30` у RAM `0x20000084` як `uint16`.

Меню змінює `W` на 10 секунд із циклічним переходом між 10 і 60. Автоматичної адаптації `W` до частоти імпульсів у відновленому коді немає.

### 5.2. Порядок дій у RTC IRQ

Суттєва частина `0x08004920`:

```c
seconds_in_period++;

pulses_this_second = 0;

bin_index++;
if (bin_index >= W)
    bin_index = 0;

window_sum = 0;
for (int i = 0; i < W; i++)
    window_sum += second_bins[i];

second_bins[bin_index] = 0;  // слот для наступної секунди

if (seconds_in_period >= W) {
    last_period_pulses = pulses_this_period;
    dose_update_pending = 1;
    seconds_in_period = 0;
    pulses_this_period = 0;
    // також скидаються деякі прапорці UI
}
```

У машинному коді індекс пересувається **до підсумовування**, а слот для нової секунди очищається **після підсумовування**. Завдяки цьому `window_sum` містить завершені останні `W` секунд. Між секундними IRQ він залишається незмінним; нові імпульси збільшують поточну комірку, але не сам `window_sum`.

Отже, це просте ковзне середнє через суму імпульсів за прямокутне вікно. Експоненційного фільтра або середнього за інтервалами між подіями у цьому ланцюгу немає.

### 5.3. Старт і зміна вікна

На старті масив секундних лічильників порожній, але знаменник відразу дорівнює повному `W`. Протягом першого вікна показ наростає у міру накопичення даних; ділення на фактично минулий час не виконується.

При зміні `W` UI встановлює прапорець `0x20000491`. Основний цикл очищає всі 60 секундних комірок та `window_sum` (`0x08003DD0–0x08003DEE`). Це початок заповнення нового вікна. У цьому блоці не скидаються `seconds_in_period`, `pulses_this_period` та `bin_index`; наступний RTC IRQ приводить індекс до нового діапазону.

## 6. Точний коефіцієнт та формула рівня

### 6.1. Константа калібрування

| Властивість | Значення |
| --- | --- |
| Початкове місце у Flash | `0x0800FCB4–0x0800FCBB` |
| Робоче місце у RAM | `0x20000008–0x2000000F` |
| Тип | IEEE-754 binary64 (`double`) |
| Байти, little-endian | `01 88 BB 7A 15 19 1D 3F` |
| Значення | `0.000111` |
| Роль у формулах і одиницях UI | µSv на прийнятий імпульс |

Це знайдене початкове значення конкретного HEX. Його наявність у коді та використання у формулах підтверджені; фізична правильність калібрування саме цієї трубки окремо не перевірялася.

### 6.2. Операції основного циклу

Блок `0x08003A56–0x08003AD4` виконує:

```c
uint32_t N = window_sum;
uint16_t W = window_seconds;
double K = 0.000111;

// У стоку спочатку виконується цілочисельне ділення!
double hour_factor = (double)(3600u / W);
double counts_per_hour = hour_factor * (double)N;

double rate_uSv_h = counts_per_hour * K;
double dose_increment_uSv = (double)N * K;

uint16_t displayed_cpm = (uint16_t)truncate(counts_per_hour / 60.0);
```

Для `W ∈ {10,20,30,40,50,60}` ділення `3600 / W` точне. Якщо в кастомі дозволити інші `W`, доцільно використовувати `3600.0 / W` або раціональну арифметику, щоб не успадкувати цілочисельне обрізання.

Еквівалентні формули для цих вікон:

```text
CPM_true    = N × 60 / W
CPH_true    = N × 3600 / W
rate_µSv/h  = CPM_true × 0.00666
rate_µSv/h  = CPS_true × 0.3996
```

CPM, який зберігається для виведення, обрізається до цілого та записується у 16 біт. Рівень `µSv/h` розраховується раніше з `double` і не проходить через цей обрізаний CPM.

### 6.3. Числові приклади

| Вікно W | Імпульсів N | CPM до обрізання | Рівень, µSv/h | Доза від N імпульсів, µSv |
| --- | --- | --- | --- | --- |
| 60 s | 0 | 0 | 0 | 0 |
| 60 s | 1 | 1 | 0.00666 | 0.000111 |
| 60 s | 23 | 23 | 0.15318 | 0.002553 |
| 10 s | 4 | 24 | 0.15984 | 0.000444 |
| 30 s | 75 | 150 | 0.999 | 0.008325 |
| 60 s | 150 | 150 | 0.999 | 0.01665 |
| 60 s | 3000 | 3000 | 19.98 | 0.333 |

Останній приклад є перевіркою арифметики. Він не встановлює фізичний верхній діапазон вимірювання приладу.

### 6.4. Рентгени

Відображення у µR застосовує множник `100` до значення в µSv. Для накопиченої дози це видно в `0x08009988–0x08009996`, для рівня — в `0x0800A904–0x0800A90E`.

```text
rate_µR/h = rate_µSv/h × 100
          = CPM_true × 0.666

dose_µR = dose_µSv × 100
```

Таким чином, згадуване раніше значення близько **0.666** відповідає коефіцієнту **µR/h на CPM** у цьому коді; коефіцієнт для µSv/h — **0.00666**. Множник 100 тут описує прийняту стоком конвенцію індикації, а не універсальне фізичне перетворення для будь-якого випромінювання.

## 7. Накопичення дози та CNT

### 7.1. Періодичне оновлення

RTC ISR виставляє `dose_update_pending` раз на `W` секунд. Основний цикл перевіряє цей однобайтовий прапорець й у `0x08003C90–0x08003CB2` виконує:

```c
daily_dose_uSv += dose_increment_uSv;
daily_cnt = (uint16_t)(daily_cnt + (uint16_t)window_sum);
dose_update_pending = 0;
```

Адреси:

- `daily_dose_uSv`: `double`, `0x20000470`;
- `dose_increment_uSv`: `double`, `0x20000480`;
- `daily_cnt`: `uint16`, `0x20000112`;
- `dose_update_pending`: `uint8`, `0x20000014`.

За нормального проходження основного циклу після кожного завершеного вікна це еквівалентно:

```text
D_µSv = кількість врахованих імпульсів × 0.000111
```

Наприклад, дві хвилини по 23 імпульси дають `46 × 0.000111 = 0.005106 µSv`. При цьому рівень наприкінці кожної хвилини — `0.15318 µSv/h`.

### 7.2. Доза та рівень мають різну роль

Віконний рівень усереднюється. Доза додає імпульсний внесок завершеними порціями; у нормальному режимі її підсумок не повинен залежати від обраного `W`.

Водночас сток має технічну особливість: ISR окремо зберігає точне число імпульсів завершеного періоду в `0x2000044A`, але досліджений основний цикл використовує для дози **`window_sum`**, а не цей знімок. У знайдених прямих зверненнях до `0x2000044A` є лише запис у ISR.

Якщо основний цикл обробить прапорець із затримкою до наступних секундних IRQ, ковзна сума вже може відповідати іншому часовому вікну. Прапорець також є одним бітом стану, а не чергою: кілька завершених періодів під час тривалого блокування основного циклу не накопичуються як кілька завдань.

Це ризики, що випливають зі структури коду. Їхню частоту на реальному приладі в цьому аналізі не вимірювали.

### 7.3. Зміна дня та добова історія

Функція `0x08002D54` читає RTC і форматує **день місяця** у рядок. Порівняння попереднього та нового рядка встановлює `0x2000046C`. Це не перевірка повного UNIX-часу або повної дати.

Коли основний цикл обробляє чергове оновлення дози і бачить цей прапорець, він обробляє добовий перехід: зсуває історію та скидає поточні дозу, CNT і максимум.

У стеку головної функції розташовані масиви по 32 елементи:

| Зсув від SP усередині main | Тип | Вміст |
| --- | --- | --- |
| `+0x140` | `uint8[32]` | Рівні/висоти стовпчиків діаграми |
| `+0x100` | `uint16[32]` | Добові максимуми CPM |
| `+0x080` | `uint32[32]` | Добові CNT; джерело поточного елемента має лише 16 біт |

Елемент 0 оновлюється поточними значеннями. Для сумарного CNT основний цикл складає елементи **0–29**, тобто 30 позицій (`0x08003D18–0x08003D30`). Розрахунок статистичної дози з CNT знову застосовує `K`; див. `0x0800CA80–0x0800CA9A`.

Ці масиви та накопичувачі є RAM-станом. Досліджений ланцюг формул та історії не містить запису вимірювань у зовнішню SPI-пам’ять або EEPROM. Під час звичайного старту відповідний стан ініціалізується заново.

### 7.4. Окрема проблема на межі дня

В емуляції відтворено таку послідовність для вже розпочатої історії:

1. У поточному збереженому елементі 0 було `100 CNT`.
2. Завершилося ще вікно з `23` імпульсами; виставлено прапорець зміни дня.
3. Основний цикл додав ці 23 до поточних накопичувачів.
4. При зсуві у попередній день потрапило старе значення елемента 0 — **100**, після чого поточні накопичувачі обнулилися.

Таким чином, остання додана порція не потрапила до збереженого добового CNT у цьому шляху виконання. Це підтверджена поведінка ізольованого блоку коду при заданому стані. Реальний розподіл втрат на межах дня залежить від часу IRQ, читання RTC і виконання main.

## 8. Максимум і шкала накопиченої дози

### 8.1. Максимум

`0x08003AEA–0x08003AF8` порівнює поточний 16-бітний CPM (`0x20000196`) із поточним максимумом (`0x2000011A`) та залишає більше значення.

Це максимум **усередненого за W секунд CPM**, не максимум миттєвої частоти між двома імпульсами. Перерахунок цього максимуму для статистики використовує `max_CPM × 60 × K` у `0x0800C9EE–0x0800CA16`.

Власне ковзне вікно вже є способом усереднення рівня; окремого експоненційного AVG у відновленому вимірювальному ланцюгу не знайдено.

### 8.2. Число 5.0 — інша величина

За адресою RAM `0x20000080` початково лежить `float 5.0` (Flash `0x0800FD2C`). Воно використовується у шкалі накопиченої дози, а також редагується через UI. Це інший параметр, ніж коефіцієнт `K`.

Блок `0x08003A02–0x08003A3C` проходить `i = 1..10` і перевіряє:

```text
configured_limit × i / 10 < current_daily_dose
```

Якщо умова істинна, зберігається рівень стовпчика `i` у `0x20000495`. Цей 10-рівневий показ потім використовується в графіці накопиченої дози. Його не слід плутати з фіксованими порогами кольору рівня 0.4/0.9.

## 9. Коли жовтіють і червоніють LED та значок

### 9.1. Точні межі

| Внутрішній рівень, µSv/h | Клас | LED за прийнятим зіставленням каналів плати | Варіант значка |
| --- | --- | --- | --- |
| `< 0.4` | 1 | Зелений, канал PA1 | Перший |
| `≥ 0.4` і `≤ 0.9` | 2 | Жовтий, PA1 + PA0 | Другий |
| `> 0.9` | 3 | Червоний, канал PA0 | Третій |

**Рівно 0.4 — жовтий. Рівно 0.9 — теж жовтий.** Червоний починається строго вище 0.9.

Гістерезису або витримки часу в самих функціях вибору кольору немає. Затримку реакції створює вимірювальне вікно та період оновлення суми.

Для LED константи містяться як пари 32-бітних слів у literal pool:

| Значення | Молодше / старше слово | Адреси Flash |
| --- | --- | --- |
| 0.4 | `0x9999999A`, `0x3FD99999` | `0x08009134`, `0x08009138` |
| 0.9 | `0xCCCCCCCD`, `0x3FECCCCC` | `0x08009140`, `0x08009144` |

Для значка є окремі копії тих самих значень:

| Значення | Адреса `double` у Flash | Байти little-endian |
| --- | --- | --- |
| 0.4 | `0x0800FB18` | `9A 99 99 99 99 99 D9 3F` |
| 0.9 | `0x0800FB10` | `CD CC CC CC CC CC EC 3F` |

### 9.2. LED: від порогу до ніжок

Функція `0x080090D4` записує клас у `uint8` за адресою `0x20000478`:

```c
if (rate < 0.4)
    led_class = 1;
if (rate >= 0.4 && rate <= 0.9)
    led_class = 2;
if (rate > 0.9)
    led_class = 3;
```

У таймерному обробнику `0x08004A84`:

- `pending_indication != 0` означає, що від попередньої обробки були імпульси; цей накопичувач очищається;
- якщо індикацію дозволено (`0x20000012 != 0`), клас 1 викликає toggle GPIOA з маскою `0x0002`, клас 2 — з масками `0x0002` та `0x0001`, клас 3 — з маскою `0x0001`;
- при відсутності подій обидва виходи PA1/PA0 встановлюються у `1`, що відповідає вимкненню цих каналів за активного низького рівня.

Маски виходів і керування ними підтверджені кодом та емуляцією. Назви «PA0 червоний / PA1 зелений» відповідають попередньому зіставленню плати; фізичні кольори каналів у цьому дослідженні заново не перевірялися.

Оскільки `pending_indication` лише перевіряється на ненульове значення, кілька імпульсів між двома обробками індикації можуть дати одну дію LED. Самі лічильники імпульсів при цьому збільшуються для кожного прийнятого спрацювання.

### 9.3. Значок: окрема функція з тими самими межами

`0x0800A9A4` самостійно читає рівень `0x20000070` та обирає зміщення варіанта графіки:

```c
if (rate < 0.4)                  variant_offset = 0x0000;
else if (rate <= 0.9)            variant_offset = 0x1800;
else                            variant_offset = 0x3000;
```

Потім вона двічі викликає renderer `0x0800AFE4`: для верхньої та нижньої частини графіки. У першому виклику `r0 = 15`, `r1 = variant_offset`, `r2 = 2`; у другому `r1 = variant_offset + 0x0B9A`. Цю функцію головного екрана викликає `0x0800AB38`.

Сам вибір варіанта і пороги доведені HEX. Піксельні дані цих растрових варіантів містяться в ресурсах; визначення порогів не потребує їхнього відновлення.

### 9.4. Перерахунок меж у CPM

За стоковим коефіцієнтом:

```text
0.4 / 0.00666 = 60.060060... CPM
0.9 / 0.00666 = 135.135135... CPM
```

При `W = 60 s`, коли число імпульсів у хвилині ціле:

| CNT за вікно / CPM | Колір |
| --- | --- |
| 0–60 | Зелений |
| 61–135 | Жовтий |
| 136 і вище | Червоний |

При інших вікнах крок рівня відрізняється. Наприклад, `W = 50 s`, `N = 113` дає істинні `135.6 CPM` і `0.903096 µSv/h`: колір уже червоний, хоча збережений цілий CPM дорівнює 135. Тому переносити пороги в кастом як порівняння лише з обрізаним CPM не слід.

## 10. Особливості стоку, які впливають на покази

### 10.1. CNT має 16 біт

Поточний добовий CNT записується через `STRH`, тобто працює за модулем 65 536. Після `65 535 → 65 536` показ може стати нулем. Добові елементи історії мають 32 біти, але наповнюються вже обрізаним 16-бітним поточним CNT.

Перевірений приклад:

```text
CNT перед додаванням:        65 530
Нові імпульси:                   10
CNT після додавання:              4
Dose після додавання:       7.27494 µSv
```

Доза як `double` в цьому прикладі продовжує зростати правильно. Проте історична доза, відновлена з переповненого CNT, буде занижена. Це узгоджується з можливістю окремого «перекидання» лічильника, не доводячи причину кожного раніше поміченого UI-збою.

Один повний оберт CNT відповідає `65 536 × K = 7.274496 µSv`. Це програмна межа цілого лічильника, а не межа діапазону трубки.

### 10.2. CPM також має 16 біт

Після перетворення `counts_per_hour / 60` код зберігає результат через `STRH`. Наприклад, при `W = 60`, `N = 65 536` внутрішній рівень становить `436.46976 µSv/h`, а збережений CPM уже дорівнює 0. Це контрольний арифметичний приклад, а не твердження про точність приладу на такому рівні.

Максимум CPM успадковує це обмеження.

### 10.3. Екран може утримувати попереднє значення

Функція `0x0800A84C` має кеш показу:

- для Sv/R кеш вихідного значення оновлюється лише якщо внутрішній рівень `>= 0.01 µSv/h`;
- для CPM кеш оновлюється лише якщо поточний CPM ненульовий.

В іншому разі код може відобразити попереднє кешоване число. В емуляції при внутрішньому рівні 0 залишився попередній кеш `0.15318`, а при CPM 0 залишилося попереднє значення 23.

Формула рівня та класифікація LED/значка читають актуальний внутрішній рівень; утримання числа є окремою властивістю відображення. Воно не означає, що нульові імпульси враховуються як попередня доза.

### 10.4. Незавершені періоди та скидання

Доза й CNT додаються порціями по `W` секунд. Імпульси поточної незавершеної порції ще можуть бути тільки у секундному буфері/лічильниках. На звичайному ребуті RAM-стан ініціалізується заново.

Команда скидання в UI очищає дозу, CNT, максимум, історичні масиви та секундні комірки. Зміна `W` окремо очищає секундний буфер, як описано вище. Кастом має самостійно визначати політику збереження цих даних.

## 11. Перевірки виконанням оригінального коду

Перевірки проводилися на байтах дослідженого HEX. Основні результати:

| Перевірка | Результат |
| --- | --- |
| Один callback PB6 | `pending=1`, обидва імпульсні 16-бітні лічильники = 1, `bins[0]=1`; `window_sum` ще 0 |
| Наступний RTC IRQ | Індекс = 1, `window_sum=1`, лічильник поточної секунди скинуто |
| `W=60`, 23 імпульси | `0.15318 µSv/h`, `23 CPM`, приріст `0.002553 µSv` |
| Дві послідовні хвилини по 23 імпульси | Два оновлення на 60-й/120-й секунді; CNT = 46, доза = `0.005106 µSv` |
| `W=10`, 4 імпульси | `24 CPM`, `0.15984 µSv/h` |
| `W=30`, 75 імпульсів | `150 CPM`, `0.999 µSv/h` |
| Переповнення `CNT=65530`, додавання 10 | CNT = 4; доза продовжує накопичуватися |
| Межа 0.4 | Клас 2, offset значка `0x1800`, toggle PA1 і PA0 |
| Межа 0.9 | Клас 2, offset значка `0x1800`, toggle PA1 і PA0 |
| `0.900000001` | Клас 3, offset значка `0x3000`, toggle PA0 |
| Нульовий рівень після ненульового | Внутрішній рівень нульовий; кеш відображення може залишитися попереднім |
| Перехід дня зі збереженими 100 CNT і новими 23 | У попередній елемент історії перенесено 100, новий поточний = 0 |

Для перевірки знаків порівняння також окремо виконано оригінальні програмні функції:

| Адреса | Операція, встановлена виконанням |
| --- | --- |
| `0x08000434` | `double a < b` |
| `0x08000448` | `double a <= b` |
| `0x0800045C` | `double a > b` |
| `0x08000470` | `double a >= b` |
| `0x08001BCC` | Множення `double` |
| `0x08001358` | Ділення `double` |
| `0x08000BCC` | Додавання `double` |

Це, зокрема, усуває неоднозначність, чи є жовтим/червоним значення рівно на порозі.

## 13. Що можна перенести у кастом

Підтверджена основа для сумісних числових показів:

```c
// Значення стокового образу; у кастомі може бути налаштовуваним.
const double K_uSv_per_count = 0.000111;

rate_uSv_h = window_counts * 3600.0 / window_seconds * K_uSv_per_count;
dose_uSv   = total_counts * K_uSv_per_count;

if (rate_uSv_h < 0.4)
    colour = GREEN;
else if (rate_uSv_h <= 0.9)
    colour = YELLOW;
else
    colour = RED;
```

Для кастому доцільно накопичувати точний CNT широким цілим лічильником і виводити з нього дозу, незалежно від ковзного вікна рівня. Це усуває прив’язку накопичення дози до своєчасності main та не потребує копіювання 16-бітних переповнень стоку. Округлення і форматування слід робити на етапі показу.

Формат нових журналів, курсори, маркери ребуту та прив’язка похвилинних/погодинних даних до встановленого часу залишаються окремими рішеннями проєкту. Стокові формули не визначають цей формат.
