# Geiger-2: індекс зовнішньої пам’яті та оригінальних викликів

Дата аналізу: 2026-10-06. Звірено компактний архів, попередній continuation-export v9 та архів витягнутих PNG.

## Контрольні файли

- Оригінальна EN 4.1.17: `Port-4.1.17-original.hex`, SHA-256 `89368E9B3D8789D641D0D9756971CEA92EA10902EA8FEFFAC604745A0791D6D0`.
- Прийнята робоча v9: `port-20261006-0747-settings-sun-v1.hex`, SHA-256 `43FFF435E717E987107A8442EF94F4B7DD0E75CE4C734186DEEFD10D570D47D9`. Вона побайтно збігається з `Port-4.1.17-v9-settings-sun-current.hex` із компактного архіву.

- Дамп має запрограмовані ділянки у банках `00`, `01`, `07`–`0F`; детальні межі щільних 4-KiB секторів наведено нижче. Межа сектора не означає межу окремого файла/ассета.

## Куди вели оригінальні виклики

Оригінальні растрові виклики перелічених ділянок ведуть у прошивковий диспетчер `0x0800AFE4`; він викликає читач ресурсів і RGB565-блітер. Адреси `0x0800....` — код STM32, а не адреси картинки у зовнішній пам’яті.

| Виклик STM32 | Ресурс за оригінальною картою | Розмір / позиція | Що зроблено у прийнятій v9 |
|---:|---|---|---|
| `0x0800A72E` | `0x0B8A8`, µSv/h | 2,400 B, 60×20, (60,56) | Bitmap-виклик замінений на текстовий renderer 7×10 |
| `0x0800A752` | `0x0CB68`, CPM | 2,400 B, 60×20, (60,56) | Bitmap-виклик замінений на текстовий renderer 7×10 |
| `0x0800A776` | `0x0C208`, µR/h | 2,400 B, 60×20, (60,56) | Bitmap-виклик замінений на текстовий renderer 7×10 |
| `0x0800A250` | `0x0690`, DOSE µSv | 840 B; 21×20 | Замінений текстовою міткою µSv |
| `0x0800A278` | `0x09D8`, DOSE µR | 840 B; 21×20 | Замінений текстовою міткою µR |
| `0x0800A2A2` | `0x0D20`, DOSE CNT | 840 B; 21×20 | Замінений текстовою міткою CNT |
| `0x0800B9EE` | `0x0604`, центральний значок Settings | 900 B | Базова растрова гілка лишилась; пізні RGB-експерименти відхилені |
| `0x0800BA0A` | `0x0302`, лівий значок Settings | 720 B | Базова растрова гілка лишилась |
| `0x0800BA26` | `0x032A`, правий значок Settings | 800 B | У прийнятій v9 змінена пара вибору ресурсу: offset `0x032A → 0x0CF8`, selector `11 → 17`, X `130 → 134` |

Для Settings відомі логічні ключі та довжини з коду, але їхню фізичну адресу у SPI NOR не можна встановити лише за цими трьома числами. Їх треба зіставити з фактичним читанням SPI/логікою диспетчера; не робити висновок, що фізична адреса дорівнює `0x70000 + offset` для будь-якого виклику.

Не плутати три виклики малювання Settings (`B9EE`, `BA0A`, `BA26`) із сусідніми пост-рендерними state helpers (`BA2C`, `BA40`, `BA48`). Прямі підміни helper-викликів через `0x0800F91E` спричиняли перезапуск. Експеримент `settings_sun_three_v2` перенаправляв усі три значки на один 12×12 ресурс `0x0364`, selector 22; це окрема експериментальна збірка, не прийнята v9.

## Що змінилося в v9 проти оригінального HEX

Порівняння перевірених файлів: 3,026 байтів відрізняються. За 4-KiB сторінками MCU Flash зміни розподілилися так:

| Діапазон MCU Flash | Змінені байти | Основний вміст змін |
|---:|---:|---|
| `0x08004000–0x08004FFF` | 1 | одинична зміна |
| `0x08009000–0x08009FFF` | 52 | корекція/позиціонування головних числових полів |
| `0x0800A000–0x0800AFFF` | 198 | заміна головних одиниць і DOSE-підписів на текст; перенаправлення викликів |
| `0x0800B000–0x0800BFFF` | 296 | Settings/Time/Date/Energy labels та виклики renderer-ів; налаштування сонячного значка |
| `0x0800C000–0x0800CFFF` | 78 | меню Energy/Statistics та пов’язані відключення/перенаправлення |
| `0x0800D000–0x0800DFFF` | 98 | підписи й поля меню часу/дати |
| `0x0800F000–0x0800FFFF` | 2,303 | додані renderer-и, рядки та растрові шрифти/гліфи в MCU Flash |

Важливо для нового плану: ці 3,026 змін — тільки у внутрішньому HEX STM32. У v9 не відновлювали й не переписували зовнішній дамп SPI NOR; порожні ресурси були обійдені текстовим рендерингом. Тобто для стратегії «оригінальний HEX + відновлена SPI NOR» слід починати з оригінальної прошивки, а v9 використовувати як довідник перевірених текстів, геометрій і рішень.

## Межі доказів і наступне для повного індексу

- Відомі 16 растрових сегментів з геометрією перелічені вище; це не повний каталог 1 MiB.
- SPI-журнал містить унікальні пари адреса/довжина, зокрема послідовності коротших читань зі зсувом `0x100`. Це фрагменти SPI-запитів і не обов’язково окремі файли або ассети. Їх треба агрегувати за початковою адресою/довжиною виклику, а не рахувати кожен рядок як самостійне зображення.
- Адреса ресурсу `0xD99E` згадується в карті, але довжина/геометрія ще невідомі.
- Перед записом будь-якого відновленого образу потрібна окрема таблиця: логічний ідентифікатор, фізична адреса, довжина, доказ із виклику/логу, SHA-256 вихідного фрагмента та план заміни. Цей звіт не змінює ані HEX, ані BIN.
