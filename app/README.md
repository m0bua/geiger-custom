# Device Monitor

Small browser-only client for firmware protocol v1. It has no build step, dependencies, or native components.

## Run

For desktop serial access, serve the repository from `http://localhost` or HTTPS in a browser with Web Serial support (tested in Chrome/Edge and Firefox). Android uses the separate **Connect USB** WebUSB path for CP210x `10C4:EA60`; this path needs physical phone testing. iOS supports the PWA interface but has no implemented USB transport. From the repository root, run:

```powershell
python -m http.server 8000
```

Then open `http://localhost:8000/app/`. The page uses a classic deferred script (no ES-module import), so the UI itself can also be opened as `file://`; Web Serial may still require localhost/HTTPS depending on browser security policy.

## Standalone release

From the repository root, run `python tools/build_release.py`. The script builds the current firmware with the installed ARM GCC toolchain, then packages the app, firmware image, and all manual SVG illustrations into `dist/Dosimeter-App.html`. If Node.js/`npx` is installed, Terser compresses and mangles the bundled JavaScript; on CI this minifier is required automatically. Pass `--version YYYYMMDDhhmm` to embed the same timestamp used by the release tag in About; local builds default to `local`. **Quick flash** is an accordion item before **Flash firmware** and contains a duplicate **Backup FLASH** dump button plus the embedded firmware action. The backup button uses the same verified FLASH dump flow as the Dumps section. Quick flash runs the same image validation, verification, and startup flow as a selected image. The containing item opens by default when the image is embedded; otherwise **Flash firmware** opens. Web Serial still requires a supported browser context; if direct `file://` access is blocked, serve the single HTML file from localhost or HTTPS. Set `ARM_GCC_BIN` or pass `--toolchain` to select ARM GCC on a CI runner. The manual GitHub Actions workflow creates a published prerelease tagged `YYYYMMDDhhmm` and titled `APP-YYYYMMDDhhmm`; it attaches both `Dosimeter-App.html` and `firmware.bin`, and uploads both as workflow artifacts.

The firmware currently speaks USART1 at 115200 8N1 over the board's USB-UART bridge. Select its serial port in the browser prompt. The session line displays the USB VID:PID to help identify the bridge. Opening the port may affect DTR/RTS on some bridges and can reset the device; the app waits for startup and retries `HELLO` automatically.

The **Firmware** tab has exclusive accordion sections. In the standalone release they are ordered **Quick flash**, **Flash firmware**, **Reboot**, and **Dumps**; Quick flash and its **Backup FLASH** button appear only when the app contains a firmware image. Otherwise **Flash firmware** starts expanded. Opening another section collapses the previous one. The **Activity** log stays visible below the accordion. Both manual flashing and the local-build shortcut recommend dumping and saving FLASH before programming. Firmware actions reuse the active transport when connected; otherwise they choose WebUSB on Android and Web Serial on desktop. Android uses the same CP210x adapter, reopening it at 115200 8E1 for ROM operations and explicitly applying DTR/RTS only during firmware actions. After programming, the app now asks the STM32 ROM bootloader to **GO** to `0x08000000` when the command is supported; the **Firmware** action also checks for ROM mode and tries GO before its signal-based fallback. This avoids treating DTR=RTS high (used in the bootloader-entry sequence) as the application-start signal. **Bootloader** reports ROM mode only after ACK `0x79`. FLASH/EEPROM dumps use STM32 ROM `Read Memory`; programming validates the image, checks the STM32 device ID, erases only covered pages, writes them, and verifies by default. ROM GO and the signal fallback still need physical confirmation on Android. The earlier Web Serial Firmware ↔ Bootloader round trip was preliminarily confirmed; repeat cycles are still needed.

When the app is served from the project at `http://localhost:8000/app/`, a **Flash local build** shortcut appears above Reboot if a local PlatformIO firmware image exists. It fetches the latest BIN on click, then uses the same validation, verification, programming, and startup flow as a manually selected image. It does not invoke PlatformIO; compile the firmware first. The shortcut stays hidden on hosted pages, `file://`, or when the build file is unavailable.

The same tab accepts STM32 `.hex` and `.bin` images. HEX records, checksums, address range, overlap, flash capacity, and STM32L051 reset vectors are checked before enabling Flash; BIN size and vectors are checked too. A small identity label recognizes checksums of the canonical 64 KiB project flash image (HEX gaps normalized to `0xFF`) for fully or partially compatible JS protocol versions, marker-bearing but unlisted project images, and the stock-family signature shared by the supplied `Port-4.1.17.hex`, `Port-4.1.16.hex`, `EN-3.1.18-(only-Windows).hex`, and `RU-3.0.19-(only-Windows).hex`. Colors distinguish compatible (green), partially compatible (yellow-green), unlisted project/stock (yellow), and unknown (red); all structurally valid images remain flashable. HEX files use RTS low/DTR high; BIN files first enter ROM with the confirmed RTS low/DTR high sequence, then try RTS low/DTR low after synchronization. If that BIN state drops the ROM link, the flasher re-enters ROM with the stable RTS low/DTR high state before erasing anything. It checks the device ID, erases only flash pages covered by the image, and writes those pages. **Verify after programming** is enabled by default and reads every written page back for byte comparison. After a verified write, compatible project firmware is started and checked with `HELLO`; partially compatible project images also get a `HELLO` check only; a recognized stock image is started and checked using `fwid` at 115200 8E1 (expects a six-byte numeric dotted version); unlisted project/unknown firmware gets the start signal without an application-level startup check. Reboot actions also disconnect after completion. If the port refuses to close, the status and top-right button remain on **Disconnect** so the close can be retried.

The **Dumps** section downloads raw binary images named `<flash|eeprom|spi>-YYYY-MM-DD_HH-MM-SS.bin` using local time. FLASH (64 KiB) and EEPROM (2 KiB) use STM32 ROM bootloader `Read Memory` and do not depend on the running application protocol. The app sends the firmware-start signal after reading and reconnects if the device was connected before the dump. SPI uses protocol opcode `GET_SPI_DUMP_PAGE` in chunks up to 58 bytes; its button is enabled only while connected firmware advertises that capability and reports SPI logging enabled and ready. SPI data is exported as the full detected chip image, including unused bytes. The firmware read API supports the populated MX25R8035F 1 MiB device. Dumps can take a while over UART; progress is written to the shared Firmware **Activity** log, which also records reboot and flash operations.

The Overview and Logs use the device's UNIT and prefix settings. The rate chart follows the selected rate unit. Logs is placed before Settings and Debug. Debug mirrors the device pages in one table: time/RTC with SPI identification, power readings, and physical log counts/store state; the three sections are expanded by default and can be collapsed independently. Counts show stored records; virtual aggregates and live points may add visible rows without a storage write. Settings compares the device RTC against the computer's local clock and can synchronize it when firmware advertises `SET_RTC`; the rate's blue startup state includes a 30-pulse progress bar using the existing status count. Dose values use up to six digits. Settings reads and applies persistent options, including RATE ROW 2 and DOSE ROW 2; unavailable duplicate row values stay visible but disabled. Device actions require protocol support. This app supports custom firmware on Mira Safety Geiger-2 and Milerd HiStand devices. **Manual** contains the app quick-start and usage notes. **About** shows the build version, recent changes, and known hardware/app limitations. Release builds display the same `YYYYMMDDhhmm` timestamp as their URL/tag; local builds display `local`. The previous `#instructions` URL hash redirects to Manual for compatibility.

Logs lists MINUTES, HOURS, DAYS, and ALERTS from the same canonical reader as the device graphs. The app fetches five records at a time (transport pages 2+2+1) until it has 60 minute, 24 hour, 30 day, or 5 alert records. Each Load more fetches another full group of the same size. Tabs and dates retain their records; the current point refreshes every second and revisiting a current log catches up newer records. Historical date requests begin at the last record before the end of the selected day. Average and maximum CPM are received from firmware; JavaScript does not merge or re-aggregate records.

Protocol operations:

- `GET_STATUS` (2): empty request; response retains the original 25-byte status and appends `count_total:u32` for the device-style debug CNT value. Old clients can ignore the appended bytes.
- `GET_LOG_INFO` (5): empty request; 30-byte response: `status:u8 | log_memory:u8 | stored_counts:u16[4] | calendar_valid:u8 | calendar_seconds:u32 | spi_size_mb:u8 | spi_ready:u8 | jedec:u8[3] | rtc_status:u8 | clock_source:u8 | uptime_seconds:u32 | log_format:u8(2) | read_source:u8 | storage_error:u8 | seconds_count:u8`. Stored counts follow MIN/HOUR/DAY/ALERT; live/derived points are not counted as stored slots. Memory values are EEPROM=0, SPI=1, OFF=2; OFF remembers its read source.
- `GET_LOG_PAGE` (6), v2 (capability bit 8): request is `type:u8 | count:u8 | m_seconds:u32 | cursor_time:u32 | cursor_epoch:u16 | cursor_skip:u16 | date_limit:u32` (18 bytes). Types are MIN=0, HOUR=1, DAY=2, ALERT=3. Count is 1–2; m is a multiple of 60 seconds, at most 7 days. Initial cursor is `time=0xffffffff, epoch=0xffff, skip=0`. `date_limit=0` selects latest; otherwise it is the inclusive date bound. Response: `status:u8 | type:u8 | count:u8 | more:u8 | next_time:u32 | next_epoch:u16 | next_skip:u16 | records[count]`.
- Canonical record (25 bytes): `timestamp:u32 | CNT:u32 | AVG_CPM:u32 | MAX_CPM:u32 | covered_seconds:u32 | epoch:u16 | flags:u8 | id:u16`. Flag bits: available=0, partial=1, live=2, calendar-valid=3. An alert’s covered seconds is its duration. ID distinguishes same-minute events. A non-calendar timestamp is uptime, not an invented calendar date. The cursor remains stable when a new minute is inserted.
- `GET_SPI_DUMP_PAGE` (7): request is `offset:u32 | length:u8`; length is 1–58. Response is `status:u8 | offset:u32 | length:u8 | data[length]`. Capability bit 5 announces SPI dump support; requests require SPI as the selected read source and a ready NOR device (including recording OFF).
- `SET_RTC` (8): request is `seconds_since_2000:u32` little-endian using the computer's local wall-clock time; response contains status. Capability bit 6 announces support.

Firmware builds and tests:

```powershell
python tools/build_firmware.py --test-support
python tools/test_log_engine.py
node tests/test_app_logs.cjs
python tools/build_firmware.py
```

The manual ARM build uses the installed PlatformIO toolchain without updating the global PlatformIO cache. It writes ELF/BIN/map/stack-usage files under `.pio/scratch`. Firmware tests emulate storage and resets; real hardware still needs validation. `LOG MEMORY` migrates records before saving a new EEPROM/SPI choice. OFF pauses recording while retaining access to its previous source. A memory change may take longer than a normal setting, so the app allows 120 seconds for that operation.
